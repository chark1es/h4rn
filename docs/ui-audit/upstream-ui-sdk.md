# Upstream notes for UI SDK

Bugs found in `@ui-sdk/core` / `@ui-sdk/react` 0.1.0-beta.17 that we work around locally. Nothing here has been filed upstream yet.

## Touch-screen sheets slide under reduced motion

On a touch screen (`(hover: none) and (pointer: coarse)`), `driver: "auto"` picks the scroll-snap driver for bottom sheets (`foundation/popups/sheet.js`, `usesScrollSnap`). That driver's `open()` and `close()` (`foundation/popups/sheet-scroll-snap.js`, `animateTo`) always run the ~520 ms spring translate and never check `reducedMotion()`. Only the pointer driver's `startSettle` (`sheet-pointer.js:134`) takes the fade path. This affects every sheet presentation: Drawer, Dialog `presentation="sheet"`, and Menu and Select `presentation="sheet"` or `"auto"`. Menu, Select and Dialog have no `driver` option to opt out. To reproduce, render `<Menu presentation="sheet">` and open it in Chromium with Playwright at 390×844, `hasTouch: true`, `reducedMotion: "reduce"`. The content gets a running `translate` animation and slides up from the bottom edge over ~580 ms; close slides out the same way. Expected, per `docs/components/drawer.md` ("Styling" and the accessibility notes): "The drawer respects reduced motion, fading instead of sliding." Our workaround is `skipReducedSheetMotion` (`apps/ui/src/lib/sheet-motion.ts`). It goes on the content of `ui/menu.tsx`, `ui/select.tsx`, `ui/dialog.tsx` and `ui/sheet.tsx`, and calls `finish()` on the sheet's script animations once the SDK's first-frame layout is done (and right away on close). Remove it once the scroll-snap driver honours reduced motion.

## A touch-screen Select sheet stays off screen under reduced motion

With reduced motion on, a Select with `presentation="auto"` (or `"sheet"`) on a touch screen opens with `data-open` and `data-driver="scroll-snap"`, but the listbox stays below the viewport for as long as it is open. In Chromium with Playwright at 390×844, `hasTouch: true`, `reducedMotion: "reduce"`, open `/settings/appearance?mock=1` and tap "Interface language". The listbox stays at y≈964, and its snap host (the listbox's parent) stays at `scrollTop` 0 of 381. With normal motion it settles at y 607. It fails with and without our `finish()` workaround above.

Cause, as far as we can tell from `foundation/popups/sheet-scroll-snap.js`: `open()` sets the host's `scrollTop` to the open snap point and starts the slide. In the same frames the Select content resizes, and the sheet's `ResizeObserver` calls `relayout()`, which runs `layout()`. `layout()` removes the snap markers and adds new ones. Chromium then re-snaps the `scroll-snap-type: y mandatory` host to the closed marker at 0. `relayout()` only puts `scrollTop` back when it restarts the slide (`moving.to !== point.extent`) or when no slide is running. With normal motion our popup's 0.96 scale-in changes the measured size, so the slide restarts and resets `scrollTop`. Under reduced motion that transition is off, so the target matches, nothing resets `scrollTop`, and the sheet settles at its open snap point while scrolled to the closed one. Menu and Dialog sheets don't resize after they open, so they're not affected.

Expected: `relayout()` keeps the host at the target snap point after it rebuilds the markers. Our workaround is also in `skipReducedSheetMotion`. It now reacts to every `data-open` (the Select content stays mounted between opens, so a ref callback alone only ran the first time). For 30 frames after the open, if a scroll-snap sheet is open but its host is at `scrollTop` 0, it sets `scrollTop` to the first open snap marker, with no animation. That's what the driver does itself when it opens without animating. `scripts/keyboard-audit.mjs` checks it ("Select sheet on screen (touch, reduced motion)"). Remove it once the upstream driver keeps its snap position across a relayout.
