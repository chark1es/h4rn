# UI translations

h4rn's interface is available in English, Simplified Chinese (`zh-CN`), Spanish
(`es`) and Japanese (`ja`). English is the source language. The person picks a
language under **Settings → Appearance → Language** (System, English, 简体中文,
Español, 日本語). System uses the first browser or OS language h4rn has, and
English when it has none. The choice is saved on this device under
`h4rn.locale` in local storage, like the theme, and applies at once without a
reload. `<html lang>` follows the active language.

The work was split by UI area, one pull request each, so each area could be
reviewed by itself. Every area is now done (see the checklist below), and the
hard-coded text check covers the whole of `apps/ui/src`.

## How it works

- The library is [i18next](https://www.i18next.com/) with
  [react-i18next](https://react.i18next.com/), pinned to exact versions in
  `apps/ui/package.json`.
- The code lives in `apps/ui/src/lib/i18n/`. `index.ts` sets up i18next, the
  saved choice, `<html lang>` and the `Intl` formatters. The catalogues are in
  `locales/<language>/<namespace>.json`.
- There is one **namespace per UI area** (`settings`, `sidebar`,
  `composer`, …), plus `common` for words many areas share: Save, Cancel,
  Delete, Remove, Copy, Retry, the permission modes and so on.
- `commands` holds each keyboard command's one name (`commands:names.<id>`,
  keyed by `CommandId`) and group heading (`commands:groups.<group>`). The
  command palette, Settings → Shortcuts and the Keyboard shortcuts dialog all
  read them through `commandName` and `commandGroupName` in
  `lib/keybindings.ts`, so a command's name is translated in one place and a
  new command without a name fails `bun run typecheck`. The palette's own rows
  that are not a command (Switch harness…, Hide sidebar, …) live under
  `commands:palette`.
- `shell` holds the app frame's own words: the connection banner, the toast
  list, the inbox's Start a thread box, thread action failures, store failure
  toasts that belong to no page yet, and the errors the client writes itself
  (`shell:errors.<kind>`).
- `shell` also holds the system notifications h4rn raises
  (`shell:notifications.*`) and the desktop update notice (`shell:update.*`).
  A notification is worded when it is drafted, like a toast: once the system
  shows it, h4rn cannot relabel it.
- `pairing:phoneShell` holds the phone's first-launch connect screen
  (`lib/platform/mobile.ts`). It is drawn with plain DOM before React mounts,
  so it waits for the saved language's catalogue (`main.tsx` passes
  `prepareI18n()`'s promise to `preparePlatform`) and is worded once.
- A harness name is a product name in every language, except the generic ACP
  harness: `HARNESS_LABELS.acp` is a getter that returns `common:acpAgent`, so
  every reader of the map gets the active language. A sentence that names the
  harness has a second key for an agent with no product name
  (`thread:rewind.unsupportedUnnamed`, `shell:rewind.nativeUnnamed`), worded
  whole, rather than slotting "this agent" into `{{harness}}`. Chinese and
  Japanese put a space after a Latin name ("Claude Code 无法…") but not after
  their own words ("该智能体无法…").
- `library` holds the MCP servers and Skills pages (Settings → Tools) and
  the shared tool approval card. Their dialogs live in `dialogs`, and the
  pages' headings reuse the Settings navigation's names.
- A place in the app has one name everywhere. The sidebar's names are the
  source: `sidebar:inbox`, `sidebar:footer.*` (Pull requests, Issues, Usage,
  Settings) and `sidebar:hosts.title`. The phone's tab bar (`PhoneNav`) reads
  the same keys; only its pull requests tab uses the shorter
  `sidebar:phoneNav.pulls` ("PRs") so five tabs fit on a phone.
- English ships in the main bundle. Each other language loads as its own
  chunk when someone picks it, before the first render when it is the saved
  choice, so a non-English reader never sees English flash first.
- Keys are checked by TypeScript (`i18next.d.ts` types the catalogue from the
  English JSON). A missing or misspelled key fails `bun run typecheck`.
- A key with no translation falls back to English, never to the raw key.
  An empty value is kept as is, not replaced by English: a scope with no
  second line. The catalogue test allows `""` only where English is empty
  too.

## Adding a string

1. Add the English text to `locales/en/<namespace>.json`, nested under the
   page or component it belongs to, for example
   `settings.json → worktrees.remove.title`.
2. Use it in a component with
   `const { t } = useTranslation(["settings", "common"]);` and then
   `t("worktrees.remove.title")` or `t("common:cancel")`. Outside React (a
   store, a validator, a toast), use `i18n.t("settings:worktrees.remove.title")`
   from `@/lib/i18n`; the component that shows the result re-renders on a
   language change because it uses `useTranslation`.
3. Use interpolation for values: `"Remove {{name}}"` with
   `t("…", { name })`. Never build a sentence by joining strings.
4. For counts, use plural keys and pass `count`: English needs `_one` and
   `_other`, Spanish `_one`, `_many` and `_other`, Chinese and Japanese only
   `_other`. The catalogue test checks each language has exactly its forms.
5. For markup inside a sentence (code, a link, bold), write tags in the text
   (`"Run <code>{{command}}</code> in a terminal."`) and render it with
   `<Trans t={t} i18nKey="…" components={{ code: <span className="q-mono" /> }} />`.
   Don't name a tag after an HTML void element (`link`, `img`, `input`,
   `br`, …): the parser closes it at once and the text spills out after it.
6. Format dates, times, relative times, durations and numbers with the helpers
   in `@/lib/i18n` (`formatDateTime`, `formatRelativeTime`, `formatAge`,
   `formatDuration`, `formatClock`, `formatClockUnit`, `formatNumber`,
   `formatList`). They use `Intl` with the active language. `formatClock` is
   the compact, padded figure for a countdown or a table cell ("2m 05s",
   "1h 30m"); `formatClockUnit` is one amount of one unit ("450ms", "1.7s").
   How each language writes those units is a `Locale → units` map in code,
   not a catalogue string: Chinese and Japanese put their own unit word right
   after the number with no space ("2分05秒", "1小时30分", "1時間30分",
   "450毫秒", "450ミリ秒"), and every other language uses Intl's narrow units
   ("2min 05s" in Spanish). Never put a Latin "ms" or "2m05s" inside Chinese
   or Japanese text. `formatAge` is the one-unit age for a narrow column
   ("now", "5m", "3h"; "5分钟" in Chinese); word the direction around it in the
   catalogue ("wakes in {{age}}").
   An age inside a sentence ("opened by alice 3 hours ago") uses
   `formatRelativeTime` and passes the whole phrase in, as `{{when}}`. Don't
   wrap `formatAge` in a hand-built "{{age}} ago" or "{{age}}前": Japanese
   would read "3h前" with a Latin letter instead of "3 時間前".
   Join a list of names with `formatList`, never `", "`: Chinese and Japanese
   use 、. In a table cell, pass the `narrow` style
   (`formatList(names, "conjunction", "narrow")`) so it reads "a, b, c".
7. A store that shows progress, a status or an error keeps a **kind**, not
   words, and the component turns the kind into text, so a language switch
   relabels what is already on screen: `remoteStore` keeps
   `busy: { kind: "waitingForApproval" }` and `ConnectSignIn` renders
   `settings:connect.busy.waitingForApproval`. Errors work the same way, as
   `{ kind, params }`: `remoteStore`'s `error` is a `RemoteError` that
   `remoteErrorText` words (`{ kind: "sent", text }` is the relay's own text,
   shown as sent), and the app update store's is worded by
   `appUpdateErrorText`. The MCP and Skills stores keep the request that
   failed as `errorAction` beside the `ProtoError`, and
   `LibraryErrorBanner` words both: "list servers" is
   `library:errors.actions.listServers`, never text baked into the message.
   A protocol error the client writes itself
   (`clientProto("internal", "notConnected")` in `lib/client/errors.ts`)
   carries `client: { kind, params }` next to its `message` and `hint`: those
   are worded when it is raised, because it travels through every store like a
   daemon error, and `errorWords(error)` words the kind again where it is
   shown (the connection banner, the sidebar, the guest-link errors in
   Settings → Labs and Share with guest). A store that keeps such an error
   keeps the `ProtoError` itself, not its `message`, so the kind survives.
   A transport that closes for a reason it can name passes the kind in its
   close frame (`onClose({ …, error: { kind } })`), so a request still
   waiting on it fails with that kind rather than the raw close reason. Its
   words live in `shell:errors.<kind>`. A toast is worded when it is raised;
   it is gone in seconds.
8. Add the translation to `zh-CN`, `es` and `ja` in the same change, using
   the glossary below.
9. A status glyph's `label` (`AgentGlyph`, for example the footer's
   connecting orb) is also its hover `title`, and its screen-reader name when
   `labelled` is set. Translate it like a tooltip, even where nothing shows it
   as text.
10. A count shown in the text is formatted for the language as well as
    pluralised: write `{{count, number}}` in the catalogue (still pass the raw
    `count`), and pass other numbers through `formatNumber`.
11. Join sentences, such as a daemon's error and the client's note after it in
    a toast, with `joinSentences` from `@/lib/i18n/sentences`, never with
    `" "`: it puts no space after 。, so Chinese and Japanese read as one
    paragraph, and keeps the space after a daemon's English sentence.
12. A component's read props (`title`, `label`, `placeholder`, …) take no
    English default. Leave the prop optional and fall back to a key
    (`placeholder ?? t("common:choose")`), or make the caller pass it.
13. `ConfirmDialog` translates only its own Cancel; the title, body and
    button are the caller's text, so every caller translates its own.

Text that comes from the daemon (errors, skip reasons, model names) is shown
as the daemon sends it. Only the copy around it is translated.

## Phone alerts

Phone alerts are not part of `apps/ui`: the phone writes them itself, in the
phone's own language rather than the Language choice, because a notification
arrives while no page is loaded (ADR-054). Android words them in the app; iOS
in a Notification Service Extension (ADR-055).

- Connect sends the alert's facts in the FCM data message: `state`, `project`,
  `count`, the raw `thread_title` (empty when the thread has none) and, for a
  group, `thread_titles` (one per line, without duplicate raw titles). It
  also sends an English `title` and `body`, which an app from before local
  wording shows as sent. iOS gets the same fields as APNs custom keys, next to
  the English in `aps.alert`.
- The Android words live in
  `apps/mobile/native/android/app/src/main/res/values*/push_strings.xml`
  (`values`, `values-zh-rCN`, `values-es`, `values-ja`), not in
  `strings.xml`, which the Tauri template owns. `PushContent` picks the words
  from the state; `ResourceAlertWords` reads them from the resources. A
  group's title is a plural (`push_agents_need_attention`,
  `push_agents_finished`): English needs `one` and `other`, Spanish `one`,
  `many` and `other`, Chinese and Japanese only `other`.
- The notification channel's name and description come from the same file.
  After the phone's language changes, they are renamed with the next alert
  (or when Settings next reads the push status).
- An alert from a relay that sends no `thread_title`, or a state the app does
  not know, is shown in Connect's English words. On an iPhone, so is an alert
  the extension did not word: an app from before the extension, or an
  extension that failed or ran out of time.
- To add a word: add it to `values/push_strings.xml`, then to each language
  file. `PushResourcesTest` fails when a language misses a name, a plural
  quantity or a `%d`. CI's Android job runs it (`scripts/mobile-android.sh
  test`, after a build).
- The iOS words live in
  `apps/mobile/native/ios-notifications/Sources/H4rnAlertWords/Resources/<language>.lproj/`
  (`en`, `zh-Hans`, `es`, `ja`): `Localizable.strings` for the words and
  `Localizable.stringsdict` for a group's title, with the same names as
  Android (`push_finished`, `push_agents_finished`, …) and `%ld` for the
  count. `AlertWording` picks the words with the same rules as `PushContent`.
  iOS has no channel and no Live Update, so it has none of those words.
- An iOS word is added the same way, to every `.lproj`, and its name to
  `AlertWord` or `AlertCountWord`. `AlertResourcesTests` (CI's iOS job runs
  `swift test` in that package) fails when a language misses a word or a
  plural form, or when a word differs from Android's `push_strings.xml`.
- The words follow the glossary below and the web's system notifications
  (`shell:notifications.*`): an untitled thread is "A thread" / 对话 / Un
  hilo / スレッド, and the state words are the thread states' own (进行中, En
  curso, 作業中; 已完成, Terminado, 完了).

## Adding a language

1. Add its code to `LOCALES` and its own name to `LOCALE_NAMES` in
   `lib/i18n/index.ts`, and teach `matchLocale` which system tags map to it.
2. Create `locales/<code>/` with every namespace file, translated in full.
3. Run `bun run test`. The catalogue test fails until every key and plural form
   is present.
4. For phone alerts, add `res/values-<qualifier>/push_strings.xml` to the
   Android app and its folder to `PushResourcesTest`, and a `<code>.lproj`
   folder to the iOS extension's `Resources` and its row to
   `AlertResourcesTests`.

## Guards

- `lib/i18n/catalogue.test.ts`: every language has exactly the English keys,
  the plural forms its own `Intl.PluralRules` uses, no empty values, and the
  same `{{placeholders}}` and tags as English.
- `lib/i18n/hardcoded.test.ts` checks **every** `.ts` and `.tsx` file under
  `apps/ui/src` for hard-coded user-facing English, including a file added
  later. Only tests (`*.test.ts`, `*.test.tsx`), the generated protocol
  bindings (`src/gen/`) and the files in its `EXCLUDED` list are left out.
  It flags JSX text, literals rendered as JSX children, read attributes
  (`aria-label`, `title`, `placeholder`, `label`, …) and their English
  defaults in a component's props, text written straight into the DOM
  (`textContent`, `placeholder`, `setAttribute("aria-label", …)`), toast,
  option, notification and error-object `title`/`description`/`label`/
  `message`/`body` fields, store fields named `error`, `…Error` or `notice`,
  a rendered template that interpolates a store value as is
  (`` `${busy}…` ``), and lists joined with a hard-coded `", "`. URLs,
  paths, identifiers and product names are let through.
- **Adding an exclusion.** A file goes in `EXCLUDED` only when none of it is
  the app's own words: demo-mode fixtures (`lib/client/mock.ts`,
  `lib/client/mockForge.ts`, `features/ide/mockFs.ts`,
  `features/attachments/demo.ts`) and the catalogue code (`lib/i18n/index.ts`,
  `lib/i18n/i18next.d.ts`). Add the path with a one-line reason as its value.
  The suite fails if an excluded path no longer exists, so the list cannot go
  stale. A file that mixes copy with a few values that only look like prose
  stays checked and opts those lines out instead (below).
- A `", "` join that feeds data rather than display (an editable field's
  value, a request body, a `srcset`) opts out with a comment on the line
  above it: `// i18n-ignore-next-line: <why>`. The reason is required, and
  the escape covers only that line, never other text. A `<style>` element's
  CSS written through `textContent` opts out the same way.
- The same check flags prose the client writes into an error
  (`throw new Error("…")`), because its message reaches a store's `error`
  field or a toast as is. Translate it where it is thrown, with values as
  placeholders (`i18n.t("sidebar:hosts.errors.noNoiseKey", { name, command:
  "h4rnd login" })`). An internal check that can only fail on a bug (a reply
  of the wrong type, an unknown typed id, a missing `#root`) opts out with the
  same `// i18n-ignore-next-line: <why>` on the line above it.

## What stays English

Only text h4rn did not write, or that reads the same in every language, stays
as it is. Each item says why.

- **Keycaps.** Shortcut keycaps (⌘ ⇧ ↵, Ctrl, Shift, Alt, Esc, Tab, Space)
  match the keys printed on the keyboard, so they read the same in every
  language, in the palette, Settings → Shortcuts, the Keyboard shortcuts
  dialog and an empty state's "or press" line. The palette also searches each
  row's English name and synonyms, so typing "settle" or "diff" keeps working
  after a language switch.
- **Names the person or the daemon chose.** Thread titles, host, device and
  project names, and a host id the daemon names when it has no host name, are
  shown as they are.
- **Pairing codes and links.** The pairing code, the code field's
  `ABCD-EFGH` shape, the comparison code and the relay's address are values
  the person compares or types, so they are shown as they are. The link
  countdown keeps its `m:ss` form.
- **What the agent and the daemon wrote.** Messages, tool names, tool input
  and output, file names, diffs, a change set's note, a subagent's task and
  error, terminal output (including its "[process exited …]" line), daemon
  errors, hints and skip reasons, and daemon error codes in the thread's
  Details are shown as written: h4rn did not write them and cannot translate
  them. The same goes for an agent's prompt and a turn's error inside a
  notification. The shell name a new terminal tab starts with ("zsh") is a
  program name.
- **The desktop shell's own update failure.** When the Tauri shell reports why
  an update failed, its sentence is shown as sent, like a daemon error. The
  client's own "could not be installed" is translated.
- **Files, code and the previewed page.** File contents, paths, diffs, the
  daemon's diff labels ("vs main", "Turn 4f2a", "Commit 1a2b3c4"), branch
  names, commit subjects and authors, search results and the previewed page
  (its title, text and links) are content, not interface. Language names in
  the IDE's status bar (TypeScript, Rust), the encoding (UTF-8) and a glob
  example (`*.ts`) read the same in every language; plain text is worded.
- **A review comment's draft block.** Send to agent adds each comment to the
  composer draft as a block written for the agent ("Review comment · a.ts ·
  new side, line 2 · branch vs main"), so its framing stays English in every
  language. The person's own comment text is quoted as written, and the
  comment notes in the diff name their source in the active language.
- **Usage figures and provider text.** Account and provider labels, a limit's
  provider message, the daemon's failover reasons and its "nowhere to fail
  over" reason come from the provider or the daemon. The unit `tok/s` and the
  column name TTFT are technical terms. Harness names and model ids follow
  their own bullets below. A provider message that names a limit's window
  ("5-hour", "weekly") is read for that window, which is then worded in the
  language. Durations use `formatClock` (see step 6). Costs are US dollars
  with the narrow "$" in every language ("1,23 $", never "US$1.23"), in the
  figures and on the chart's axis alike.
- **MCP servers and skills.** Server, tool and skill names, a skill's
  description and version, commands and URLs (`npx -y …`, the cwd), the four
  short harness names the phone shows under a skill's switches (Claude, Codex,
  OpenCode, Anti; see product and harness names below), a conflict's reason, a
  sync status's message and hint, a server's last error and a tool call's
  error are what the daemon or registry sends. So is a server's
  `imported_from` value.
- **Product and harness names.** h4rn, Connect, Claude Code, Codex, OpenCode,
  Antigravity, GitHub, Linear and the like are names, wherever they appear
  (usage, MCP servers and skills, the thread view). Only the generic "ACP
  agent" is worded (`common:acpAgent`).
- **Commands and code in the copy.** Commands, flags, environment variables
  and placeholder examples that are code (`h4rnd token`,
  `scripts/mobile-android.sh run`, `adb reverse tcp:47800 tcp:47800`, `-y
  @modelcontextprotocol/server-github`, `search, read_file`, a git URL,
  `ws://127.0.0.1:47800/ws`) are typed as written, and the transport names
  stdio, HTTP and SSE are protocol names.
- **Model names and agent modes.** Model ids, wherever they appear (the
  composer's picker, usage, failover), and an effort level an agent names
  itself that h4rn does not know, are shown as sent.
- **A browser's own storage error.** When the browser's IndexedDB refuses a
  read or write of the secret store, its `IDBRequest.error` /
  `IDBTransaction.error` message (`lib/platform/secrets.ts`) is shown as the
  browser sends it. h4rn's own "could not be read / saved" text, used when the
  browser gives no error, is translated.
- **Thread titles and project names in a phone alert.** They are names the
  person or the daemon chose, shown as they are, like everywhere else.
- **Forge and tracker data.** Pull request and issue titles, bodies,
  comments, labels, branch names, authors, check names and descriptions, a
  linked pull request's own state word on the issue pane, and Linear's state
  names are shown as the forge or tracker sends them. The Labels and Assignees
  fields on the issue pane hold comma-separated text that is split on commas
  when saved, so they keep `", "` in every language; the read-only list of
  assignees above them uses `formatList`.
- **The secure engine's close reasons.** When the Noise engine itself closes
  the session (`onEngineClosed` in `lib/client/secure.ts`), its reason is
  the engine's own text and `closeCodeFor` reads it to choose a close code,
  so it is shown as written. So is a path status's `detail`. Every close the
  client decides itself (no route, not paired, every path closed, no secure
  path) carries a kind and is translated, as are the transport's errors
  (`shell:errors.relay*`, …).
- **Errors that only a bug can raise.** A reply of the wrong type, an unknown
  typed id, a bad chunk size or a missing `#root` keep their English message
  for the developer reading the console; each is marked
  `// i18n-ignore-next-line` with its reason.
- **Demo data.** The mock daemon, forge, workspace and attachment behind demo
  mode (`lib/client/mock.ts`, `lib/client/mockForge.ts`,
  `features/ide/mockFs.ts`, `features/attachments/demo.ts`) are sample
  content standing in for what a daemon or forge would send, so they are
  excluded from the check like that content would be.

## Translation guidelines

- Write for developers. Keep the tone of the English: short, plain, precise,
  no exclamation marks.
- Keep product terms as names: **h4rn**, **Connect** / **h4rn-connect**,
  **worktree**, **harness**, **Labs**, **CLIProxyAPI**, **MCP**, **ACP**, and
  third-party names (Claude Code, Codex, GitHub, Linear, Tailscale).
- Keep commands, flags, environment variables, scopes and code
  (`h4rnd login`, `H4RN_GITHUB_CLIENT_ID`, `Contents: read`) exactly as written.
- Follow each platform's UI conventions:
  - **zh-CN**: full-width punctuation (，。：“”), no trailing full stop on short
    labels, a space between Chinese and Latin words or numbers. A thread is
    对话 and a session is 会话.
  - **es**: sentence case, «comillas» for quoted names, and address the reader
    as *tú*, as common developer tools do. A thread is *hilo*.
  - **ja**: です/ます style for sentences, plain nouns for labels, full-width
    punctuation and 「」 quotes. A thread is スレッド.
- Spanish runs about 30% longer than English; keep labels short so rows do not
  wrap on a phone.
- The Working / Done / Settled segment never wraps. When a language's labels
  are too long for the sidebar's width (Spanish at the narrowest 240 px), the
  labels shrink with an ellipsis, the counts stay, and each tab's full name
  moves to its tooltip (`StateTabs`, `.q-seg.fit`). At wider sizes and in the
  other languages the tabs look exactly as in English.
- The thread view follows the same rule. The right panel's tabs (Changes,
  Files, Preview, Subagents) sit closer together in a narrow panel, then
  shrink with an ellipsis at the 320 px minimum, with the full name in their
  tooltip. The thread header's state word ("Requiere aprobación") gives way
  before the header's buttons, on a phone and on a narrow desktop, and keeps
  the whole label as its tooltip.
