# h4rn — Architecture Decision Records

Statuses: **Accepted** = decided by the lead engineer, final for v1. **Proposed** = recommended
by the architecture research, still open to objection. Everything below elaborates the verdicts
in [research.md](research.md) and the detail documents in [research/](research/).

---

## ADR-001: Rust core, TypeScript view-only, one WebSocket protocol everywhere

**Status:** Accepted

h4rn's entire behaviour lives in Rust crates behind a single daemon process, and the React
application is a pure view over that daemon. Every target — Tauri desktop, Tauri mobile, and the
browser build — speaks **one typed WebSocket protocol**: JSON frames for commands, events and
control, plus binary frames for PTY output and blob chunks. Tauri IPC is reserved for things only
the shell can do: keychain access, deep links, QR scanning, native file pickers, and spawning the
bundled daemon. The reason is that T3 Code's per-environment Node server exists precisely because
it can be reached one way, while a desktop-only IPC path would fork h4rn into "local mode" and
"remote mode" with different bugs; one wire format means local, Tailscale and relay connections
exercise the same serialisation, the same resume logic and the same tests. The tradeoff is that
OS integration must be modelled as an explicit, narrow side-channel instead of being available
ad hoc from the view, and that the web build can never assume a Tauri API is present.

## ADR-002: `h4rn-protocol` owns the wire types, TypeScript is generated

**Status:** Accepted

All request, event, command and error types live in the `h4rn-protocol` crate with explicit serde
representations, and TypeScript bindings are generated by `ts-rs` into `apps/ui/src/gen/` and
checked in. CI regenerates and fails on any diff. Two references make this non-optional: T3
Code's contracts package is the only thing keeping seven hand-written harness adapters coherent,
and the OrbitID research shows how quickly a wire contract drifts when a Rust server and a TS
client each hand-roll their own (`aud` as string vs array, `Bearer` capitalisation, snake_case
`/v1` objects beside form-encoded `/oauth`). Generating bindings removes a whole class of "the
UI decoded it, the daemon did not mean that" bugs, and the checked-in output makes protocol
changes visible in review. The tradeoff is a build step and the need to pin serde tagging
(internally tagged enums) so the generated discriminants are stable; a wire-compat fixture test
guards that.

## ADR-003: Event-sourced threads with local SQLite and Postgres sync

**Status:** Accepted

Every thread is an append-only event log. The daemon writes it to a local SQLite database (via
`sqlx`'s SQLite driver) as a cache and durability layer, h4rn-connect mirrors it into Postgres,
and the UI reads projections rather than events. Clients resume by passing the last sequence
number they saw. This is the most valuable thing in T3 Code: `EventStoreV2.append({commandId,
events})` with monotonic sequence plus a durable effect outbox means a daemon restart resumes a
turn instead of losing it, and idempotent command receipts mean a retried send returns the same
stored sequence rather than duplicating a turn. Keeping SQLite as a *cache* (ADR-012) means a
lost laptop disk is recoverable from the relay, while the daemon still works offline. The
tradeoff is real complexity: two stores, a sync protocol, and projection rebuilds. It is paid
once and buys correct resume, audit and multi-device consistency that a mutable-state design
cannot retrofit.

**Phase 1c note — the sequence is global, not per thread.** `ServerFrame::Event.seq` is a
durable, daemon-global, monotonically increasing number shared by every thread. `GetThread`
returns its events as `SeqEvent { seq, event }` and `Subscribe` accepts an optional `since_seq`;
a reconnecting client passes the last sequence it applied and the daemon replays every thread's
gap while holding its append lock, so replay is a prefix with no hole between the journal and
live frames. The subscribe answer carries `replay_through`, the journal head it served: a client
tells history from news by sequence instead of by arrival order, because a live frame can land
before the answer does. Keeping one global order is what lets a single socket resume all threads at
once; the alternative (per-thread cursors) would multiply resume state by thread count and still
leave cross-thread ordering unspecified.

## ADR-004: Thread tabs are Working / Done / Settled

**Status:** Accepted

h4rn deviates from T3 Code's two-way split (working + settled) by inserting **Done**, because
T3's model has no place for "the agent finished and I have not looked yet" — finished work either
stays in the active list forever or disappears the moment it completes. Definitions: **Working** =
a turn is running, queued, awaiting approval, or scheduled for auto-resume (T3's predicate set,
including the 2 s exit grace and the 60 s stale bypass); **Done** = the last turn finished
(success or error) and the user has not acknowledged it; **Settled** = acknowledged — by opening
and explicitly settling, by auto-settle after a configurable idle period (default **24 h**), or
because a linked branch merged / PR closed. A user may move any thread to any tab by hand, and a
pinned override sticks until the next turn starts, at which point execution state wins again —
T3's `settledOverride` enum (`settled`/`active`) generalised to three placements. Snooze is copied
verbatim, including its wake rules: a snoozed thread does **not** wake on run completion, only on
a raised hand (approval, question, subagent request, guest message, or a failure newer than the
snooze). The client owns placement, the daemon owns settlement, and both share one predicate set
in a crate with property tests over clock skew. The tradeoff is one more tab and a shorter idle
default than T3's 7 days, which risks surprising users; that is mitigated by a per-project
setting and a visible auto-settle timestamp.

## ADR-005: One `Harness` trait, four adapters

**Status:** Accepted

`h4rn-harness` defines a single `Harness` trait — spawn, send, interrupt, answer approval, resume,
capabilities, MCP delivery — and every harness is one adapter behind it. **Claude Code** is a
long-lived `claude -p --input-format stream-json --output-format stream-json --verbose` process
with `--mcp-config <0600 tempfile> --strict-mcp-config` and `--resume`; **Codex** is
`codex app-server` over newline-delimited JSON-RPC with per-thread `config.mcp_servers`;
**OpenCode** is `opencode serve` over HTTP+SSE with `mcp.add`; **Antigravity** is `agy acp` (ACP
stdio) as primary with stream-json as fallback. T3 Code proves both the matrix and the failure
mode: there are two generations of adapter code in-tree (legacy provider drivers plus V2
adapters) and the Claude adapter alone is 13,733 lines. One trait, one adapter, transport /
normaliser / policy / projection split into separate modules, is the only way to avoid that.
The tradeoff is that a trait must be broad enough for genuinely different approval models (Claude
and Codex are provider-initiated; ACP is client-decided), so the trait exposes capabilities rather
than assuming a lowest common denominator.

## ADR-006: One local MCP hub per daemon, injected as a single entry

**Status:** Accepted

The daemon runs exactly **one** local MCP server, `h4rn-mcp`, exposing a streamable-HTTP endpoint
on loopback with a per-session bearer token. Each harness is injected with only that hub entry;
the hub aggregates the user's own MCP servers plus h4rn's tools (`spawn_subagent`, `task_status`,
`task_cancel`, preview/render, forge operations). Remote MCP servers on other machines are
proxied through `h4rn-transport`, so a tool call crosses the same encrypted session as everything
else. Secrets never leave the host that runs the server. This is T3's design with its delivery
matrix intact: request fields for Codex and ACP, the management API for OpenCode, config for
Claude; the bearer is stored hashed, bounded by a liveness window, and revoked with the session,
and it never appears in argv where `ps` can read it. The tradeoff is a single point of failure for
all tools in a session and one extra hop for every call, which is acceptable because the hop is
loopback and the alternative — N harness-specific credential injectors — is exactly the 13k-line
adapter problem again.

## ADR-007: Terminal is `portable-pty` + headless VT + xterm.js with binary frames

**Status:** Accepted

The PTY is `portable-pty`, the screen model is a **headless VT in Rust**, the client is `xterm.js`
with the WebGL addon, transport is binary frames, and reconnect sends a snapshot instead of
replaying history. The VT crate is **`alacritty_terminal`**, chosen over `vt100` because h4rn needs
what only it provides: damage tracking and resize reflow for compact incremental frames, plus
near-complete escape-sequence coverage (alt screen, wide cells, `vim`/`less`/TUI behaviour) that
`vt100`'s smaller parser does not guarantee. It is wrapped behind an h4rn-owned `h4rn-vt` trait so
`vt100` remains a documented fallback, because `alacritty_terminal` is pre-1.0 and its API churns.
Everything else is copied from T3 Code unchanged because it is right: a 5,000-line scrollback
bound, ack-based backpressure of 8 chunks / 64 KiB per stream, smallest-viewer-wins resize, and
"no React state in the render loop". The tradeoff is two terminal state machines (server grid and
client xterm), which can diverge; the snapshot-plus-sequence handshake, and raw replay as a cold
fallback, keep divergence bounded to one reconnect.

Closing a terminal sends SIGHUP to the shell's own process id, waits for the shell to exit so it
has forwarded the hangup to its jobs (bounded at two seconds for a shell that ignores it), then does
what it always did: SIGTERM to the shell's process group, a grace period for TERM handlers, then the
handle kill (a SIGHUP by pid on Unix) and SIGKILL for the group. The hangup uses the spawned
child's pid rather than the foreground process group from `tcgetpgrp`, because a shell that starts a
job while it boots puts that job in the foreground and it would receive the hangup instead. An
interactive shell forwards SIGHUP to its jobs and skips `nohup`'d and `disown`'d ones, so background
jobs end without special-casing `nohup`, and a job that called `setsid` has left the session and
survives. Walking `ps` for session members is deliberately not done: `sess` is not portable and
signalling every member reaches jobs the
user detached. The two-second wait runs only when a hangup was actually delivered; Windows has no
POSIX signals, so closing a terminal there does not pause.

A pid belongs to the shell only until the shell is reaped, and `wait` frees it for reuse the moment
it returns. A close that signalled the pid after that could reach an unrelated process, and no
check-then-signal can close the window because the check and the signal are two steps. So the pid is
kept alive for as long as a close might signal it: the reader thread's exit path first waits for the
shell **without reaping it**, `waitid(P_PID, pid, …, WEXITED | WNOWAIT)` retried on `EINTR`, which
reports the exit and leaves the child a zombie. (`WNOWAIT` is POSIX and available on every Unix
target h4rn builds, so no `pidfd_send_signal` fallback is needed; the waitid call is documented at
the call site.) Then it takes a dedicated `reap` mutex, reaps with `child.wait()`, publishes the
exit, and releases it. The blocking `waitid` never runs under that mutex, so the close can always
take it; only the reap-and-publish and each pid-targeted signal do.
Every pid-targeted signal — the opening hangup, the primary `child.kill()`, and the pid fallbacks —
takes the same `reap` mutex, checks whether the exit is already published, and signals only while
it is not, still holding the lock. While the lock is held and the exit is unpublished the pid is
this session's live process or its unreaped zombie, never a pid another process reused. A shell that
already exited when a close runs is reaped and its exit published inside that critical section, so
its pid is not signalled at all and its status is not lost. The lock order is `reap`, then `child`,
then the stored status, then the exit.

A **confirmed reap** is therefore any of: the exit published after a reap (by the reader thread, or
by a close that reaped first), a stored exit status, or the `reap` lock being held with the exit
already published. The session's `alive` flag is not confirmation — `finish` clears it before it
waits for the shell — and a shell that ignored the hangup would otherwise be mistaken for a reaped
one and left running. The close path never waits for the child handle: the hangup wait only tries its
lock, and a busy handle falls back to the cloned
child killer, which holds its own process handle on Windows and its own pid on Unix. The session
also keeps that cloned killer so the close can end the shell through it while the reader thread is
busy. On Windows that handle kill is the only termination path the console has, and it is unchanged:
a process handle cannot be confused with a reused pid. The process-group TERM and KILL still go out
on purpose to end the shell's jobs, which can outlive it; the group id is often the shell's own pid,
so they carry the same small reuse risk, accepted for that reason. After the signals the close path
drops both PTY ends: on Windows a killed ConPTY client does not close the pseudoconsole itself, so
the master would keep the reader thread blocked in `read` and the session alive; dropping the master
closes the console and dropping the writer closes its input pipe, and together they release the
reader so the exit report runs. On Unix the drop releases a master read that outlived the killed
group. The Windows close test waits for that exit report, so a blocked reader leaks into a failure
rather than hiding behind the child handle.

Attached viewers share one PTY, so the UI marks xterm's answer to a query the program just asked
(through parser hooks for DA, DSR, DECRQM, XTWINOPS and OSC colour queries) in the input frame's
`seq` flag. Bit 0 marks a reply, bits 1-32 carry the output chunk that contained the query's
**first** byte, and bits 33-52 carry the query's index among the queries that start in that chunk:
one chunk can ask several questions (two DSR/OSC queries, a batched `OSC 4` palette query) and
xterm answers each separately. A query split across chunks names the chunk where it started, not
the one where it ended. Both parts are properties of the output stream, so every viewer that parsed
the starting chunk computes the same identity, whatever else it received or in what order. The
scanner that recognises a sequence at a chunk boundary copies xterm's parser instead of a permissive
reading of the bytes: an empty parameter list is `[0]` (the parser's `CLEAR` action resets the list
and adds a zero), an empty sub-parameter stays `-1`, values clamp to the positive int32 range, ESC
starts a new escape in every state — abandoning an open CSI, ending an OSC, DCS or string first —
and CAN and SUB cancel back to ground. The C0 controls that xterm executes (0x00–0x17, 0x19 and
0x1c–0x1f) execute in place inside escape, CSI and DCS entry/parameter states: they are not
appended to the parameters and do not change state, so a `CR`, `LF` or `BEL` between a query's
bytes cannot corrupt its signature. DEL is ignored inside those sequences. The scan runs on decoded
code points, not raw bytes, and keeps one streaming UTF-8 decoder across chunks, following xterm's
decoder byte for byte: a wrong continuation discards the sequence and reprocesses the byte from
ground, and an overlong, surrogate, BOM or out-of-range code point produces no code point at all
(never a replacement character, which would corrupt an OSC/DCS payload). U+009B starts a CSI,
U+0090 a DCS, U+009D an OSC, U+0098/U+009E/U+009F a string, U+009C is ST, and the other C1 controls
return to ground. A 0x9c byte inside a multi-byte character is therefore data, never a string
terminator, even when its lead byte arrived in the previous chunk. A split character is named by the
chunk that carried its **first** byte, so a C1 opener sent as `C2` | `9B` belongs to the chunk with
`C2` even though xterm only decodes the code point when `9B` arrives. A sequence xterm threw away is
never matched against a later hook. An OSC identifier is accepted only when every character before
the first `;` is an ASCII digit and there is at least one: xterm's `OscParser` aborts the whole
command at the first non-digit, so `10x`, ` 10` and `+10` are not `10` and cannot capture a later
query.

`term.reset()` resets the screen but not xterm's escape parser or its UTF-8 decoder, so the tracker
keeps both across a snapshot. A chunk that ends inside an OSC or DCS query is completed by the
snapshot's leading bytes (`ESC[0m` ends the OSC, an `ESC` ends the DCS) and keeps the chunk that
carried its first byte, exactly as the viewer that saw that chunk raw names it; a character split
across the boundary stays whole. Only the record of queries from before the snapshot is cleared, and
only when the snapshot chunk actually starts parsing: xterm's `WriteBuffer` schedules writes, so an
output chunk applied just before the snapshot may still be waiting. Its query keeps the chunk that
carried it. Ordinals for a chunk this viewer already parsed survive the snapshot, because the
snapshot does not unsee those queries; a query whose terminator only arrives in the snapshot keeps
its place after them, so it names the same `(position, ordinal)` pair as another viewer's. The
daemon writes the first reply naming a `(position, ordinal)` pair, from any viewer; only exact
duplicates and positions at or below the evicted high-water mark are dropped. A reply for an older
position that has not been answered yet is accepted, because it can only rescue a pending query. A
reply naming a position the daemon never sent to that viewer is ignored and leaves the record
untouched, so a bogus claim cannot suppress a real answer.

The identity comes from the output stream, so the position a viewer may claim is one the daemon
sent it, with one narrow exception for bytes it never parsed. Each viewer records the ranges it
received as raw output. A position at or below its last snapshot that lies outside those ranges is
snapshot-only for that viewer: it arrived as rendered state, never as that chunk's bytes. A snapshot
does not unsee what came before it, so a chunk the viewer parsed raw and a later resync replaced
stays its own to claim. The daemon drops a claim only when both hold: the position is snapshot-only
for that viewer, and another attached viewer that can actually write it received **that position**
raw. A viewer can write when every attached client names positions; with a legacy client attached
only the reply owner is written, so another viewer's raw copy never makes the owner's claim give
way, and before an owner exists only a viewer that names positions can answer a positioned query,
because a legacy client's unpositioned reply cannot name it. A claim therefore never waits for an
answer the ownership rule would drop, which would leave the shell with none. That other viewer has
the bytes and answers the query, and its answer must be the one written. Everything else is
accepted: a chunk the viewer parsed raw, a position no other viewer parsed raw, and the case where
every viewer saw the query only through a snapshot, where the shared `(position, ordinal)` record
still reduces the replies to one write. A viewer remembers at most 32 raw ranges (one per resync
that skipped output); forgetting the oldest makes those old positions look snapshot-only for it, so
its claim there gives way to a viewer that has them raw, or is accepted when none does. Either way
the answer record still allows one write, so the cap can never cause a second answer. A viewer
still taking its attach snapshot has received
nothing, so it never makes another viewer's claim give way. A viewer that stalled before a chunk and
catches up later therefore names the answers exactly as a viewer that kept up does: the query it
missed stays unseen, and the queries it saw are written once between them, in arrival order. The one
exception is a query xterm completes with a snapshot's leading bytes: the viewer that owns those
bytes may claim them, and with nobody else able to answer the shell is never left without an answer.
The old per-viewer attach floor guarded chunk-local numbering, and that numbering is gone; this
snapshot rule is about which bytes the viewer actually parsed, and the answer record is what keeps
the reply count at one.

Clients declare reply-position support in the attach request with `reply_positions_v2` (default
false). The field is new rather than the first `reply_positions` flag because the numbering changed
from the chunk where the query ended to the chunk where it starts: a client that only sends the old
flag is legacy, exactly like one that sends nothing, so its answers are never correlated with a
position and cannot collide with a positioned viewer's numbering. While any attached viewer has not
declared it, every reply follows the
legacy single-owner rule: the first viewer to send a marked reply that is actually written owns
them all, and its positioned replies are still validated and deduplicated. A rejected claim — a
position the daemon never sent — does not take the role, so it cannot suppress the old client's
next valid reply, and neither does a reply whose write fails: the role and the answered-position
record are only committed once the bytes reach the shell, all under the writer lock. The role moves
only when its owner detaches or is replaced, or when the last legacy viewer leaves and the
per-answer rule resumes; another legacy viewer attaching or detaching does not reset it while an
answer may be in flight. Both arrival orders therefore write exactly one answer. When every
attached viewer has declared positions, each answer is decided by its `(position, ordinal)` alone.
Acceptance and the PTY write happen under the same writer lock, so two connections cannot be
accepted in one order and write out of order. Recent chunks keep a bounded bitset of answered
ordinals: 64 chunks with 1024 answers each, deliberately fixed so memory stays constant; the tail
of a larger chunk collapses to a single high-water ordinal, and chunks older than the window
collapse into the evicted high-water mark. Those limits are deliberate, not a missing feature: a
1024-answer batch in one 64 KiB chunk is already far beyond real queries, and the collapse can only
drop answers for a chunk that has left the window. A late reply for a chunk older than the whole
window is itself the entry retired, so it can never push a still-tracked chunk out. The client
never gives up reconnecting: after
the fast backoff it retries at the capped interval, and an online, focus or visibility event retries
at once, except during the very first connect, which is not yet a retry, and while an attempt that
started less than a second ago is still opening.

## ADR-008: Attachments are a content-addressed blob store

**Status:** Accepted

Attachments live in a daemon-side blob store keyed by **BLAKE3** of the content, uploaded in
chunks streamed over the same WebSocket, and garbage-collected by reference count. This is T3
Code's attachment design deliberately improved: T3 gets the deterministic ids, path-traversal
defence, declared-size verification and per-harness delivery matrix right, but stores the same
bytes once per message, base64s every image through JSON RPC, has no streaming upload, and only
collects blobs with the thread. Content addressing fixes dedupe and makes retries free; chunked
upload fixes the 33 % overhead and whole-file buffering; refcount GC (over a grace window, with a
pending segment for in-flight uploads) fixes unbounded growth. The per-harness matrix is copied
as-is — Claude native image/document blocks, Codex `localImage` path items, ACP only when
`promptCapabilities.image` was negotiated, OpenCode `file://` for local servers only, and the
"always tell the model the absolute path" fallback with untrusted-data framing for captured
windows. The tradeoff is that a content-addressed store needs correct concurrent refcounting,
which is the risk most likely to leak or over-collect; that is why uploads are two-phase.

**Addendum (Phase 2): the delivery matrix as implemented.** The daemon stores one copy of
the bytes under `blobs/<first two hex>/<rest>`, sniffs the media type at commit (a file that
claims to be an image must decode as one), keeps a 256 px PNG thumbnail beside it, and only
materialises a per-thread copy under `attachments/<thread-id>/<hash prefix>-<safe name>` when
a message references it. `h4rn-harness/src/attachments.rs` owns the strategy enum that maps
each harness to the matrix T3 gets right:

| Harness | Images | PDFs and other files |
| --- | --- | --- |
| Claude Code | native `image` base64 block | path reference |
| Codex | `localImage` path item (Codex reads the file itself) | `mention` + path line |
| OpenCode | `file://` part for local servers | `@path` line |
| Antigravity (ACP) | image block only when `promptCapabilities.image` was negotiated | embedded text resource when `embeddedContext` was negotiated, else `@path` line |

`h4rn-harness/src/attachments.rs` is the single source for this matrix: each adapter asks
`strategy(kind, class)` and uses `media_type`/`path_line` rather than re-deriving the rules. The
prompt path line is added for every attachment on every harness — `[Attached image "x.png" is
saved at: /abs/path]` — so a model can always fall back to reading the file when a native block
was not negotiated. Phase 2 keeps PDFs on that fallback; native document blocks land with the
per-harness capability work. Text that is inlined is read through the same module: UTF-8,
UTF-16LE and UTF-16BE byte-order marks are decoded (a UTF-8 BOM is stripped), and bytes that are
not text in those encodings stay a path reference rather than becoming replacement characters.

## ADR-009: Multipath transport with a path-agnostic session layer

**Status:** Accepted

`h4rn-transport` maintains a session over several candidates at once: LAN/direct, Tailscale
(tailnet IP or MagicDNS), and the h4rn-connect relay. It probes all of them, prefers the lowest-RTT
direct path, and keeps the relay warm as a fallback rather than provisioning it on demand. Path
switching does not drop the session because the session layer — not the socket — owns sequence
numbers and acks. T3 Code's pairing and Tailscale work informs this, but its relay model (a managed
Cloudflare tunnel, provisioned and released on demand, with no application-level encryption) is
rejected: it bills per tunnel, adds a vendor, and puts plaintext at the hop. Keeping the relay warm
costs an idle connection; dropping it costs a multi-second re-provision exactly when the user's
direct path has just failed. The tradeoff is three concurrent paths' worth of probing traffic and
the need for hysteresis so a 2 ms RTT difference does not flap the active path; probes are
smoothed and a switch requires a sustained margin.

## ADR-010: Noise E2E between device and daemon; the relay sees metadata only

**Status:** Accepted

Client and daemon establish a `Noise_IK_25519_ChaChaPoly_BLAKE2s` session (the `snow` crate).
Static keys are exchanged at pairing: the QR code carries the daemon's public key plus a one-time
pairing secret, so the first handshake authenticates the daemon and cannot be relayed by a
stranger who photographs a screen. h4rn-connect routes opaque frames by connection id and learns
only metadata — who is connected, frame sizes, timing, thread counts. T3 Code has **no** E2E layer
at all: confidentiality there is TLS to Cloudflare plus DPoP-bound scoped tokens, so the relay
operator can read every prompt. For a product whose daemon runs on a user's own machine with their
own credentials, that is not acceptable. The tradeoff is that the relay cannot inspect, compress or
deduplicate payloads, so push notifications and search must be computed daemon-side, and frame
sizes need padding buckets to avoid leaking message shape. Multi-device revocation is handled with
explicit device events, not key rotation of the daemon.

**Note (mobile):** because Noise is the security boundary, the mobile shells
permit `ws://` to LAN, `.local`/MagicDNS and RFC 1918/CGNAT candidates instead
of letting Android's network security config and iOS ATS veto them. The daemon
has no TLS listener, and the pinned daemon key makes a plaintext socket no less
private than `wss://`; the relay path stays `wss://`. Android's domain config
cannot express IP ranges, so its release base config permits cleartext, with
the rationale recorded in `docs/mobile.md` and `docs/transport.md`.

## ADR-011: OIDC authorization code + PKCE, with OrbitID's quirks encoded

**Status:** Accepted

h4rn-connect authenticates users with OIDC **authorization code + S256 PKCE** using the
`openidconnect` crate, against a configurable issuer list rather than a hardcoded provider.
Desktop uses a **fixed** loopback redirect (OrbitID's TS build matches redirect URIs exactly and
does not tolerate an ephemeral port), mobile uses the `h4rn://callback` deep link registered
through OrbitID's Backend API (its dashboard refuses non-`http(s)` schemes), and the daemon uses
the **device authorization grant** (off by default on the server, and a confidential client must
authenticate at `/oauth/device_authorization` as well). The research enumerates 32 quirks and this
decision commits to handling all of them; the load-bearing ones are: normalise the issuer with no
trailing slash and mount it at the root; always send PKCE regardless of build; register
`offline_access` on the application because scopes are an allowlist; verify only
`iss`/`aud`/`exp`/`nonce` because the TS id_token omits `azp`/`at_hash`/`auth_time`/`sid`; never
request `form_post`; treat `end_session_endpoint` as optional; **single-flight refresh across
every process** because reuse revokes the family with no grace window; and treat `invalid_grant`
as "re-authenticate", not "retry". The tradeoff is a per-process single-flight coordinator and a
token store that must persist the rotated refresh token before returning, but the alternative is
users being silently logged out whenever the desktop and daemon refresh concurrently.

## ADR-012: Postgres for all relay persistence; SQLite is only a daemon cache

**Status:** Accepted

h4rn-connect persists everything in Postgres via `sqlx`, with offline query metadata checked in so
CI can compile without a live database: accounts, device pairings, environment links, the synced
event log, notification state and quota. The daemon's SQLite database is a cache and an offline
buffer, never the system of record for anything the relay owns. This split is what makes
"works offline, consistent across devices" possible: a daemon can run for weeks with no relay and
then replay its log, and a reinstall can rebuild SQLite from Postgres. T3 Code also keeps an
event log in SQLite, but it has no second store to reconcile against, so it never had to answer
which one wins. The tradeoff is a sync protocol plus schema migrations in two dialects; offline
query metadata drifts if developers forget `cargo sqlx prepare`, which CI catches. A single store
would be simpler and strictly worse for the product's core promise.

## ADR-013: CodeMirror 6 for the editor, LSP explicitly out of scope

**Status:** Accepted

The in-app editor and diff viewer use **CodeMirror 6**, not Monaco. Monaco is roughly an order of
magnitude larger, assumes a desktop-class browser, and is awkward inside mobile WebViews and
WebKitGTK; CodeMirror 6 is modular, works in every Tauri WebView, and its merge/diff view is good
enough for reviewing agent edits. The scope is deliberately "look at and lightly edit the file the
agent touched", with diffs scoped to a checkpoint or run exactly as T3 Code scopes them, rather
than a general IDE. **LSP is out of scope** for v1: no language servers, no completions, no
diagnostics beyond what the agent's own tooling reports. The same holds for a debugger and an
extension host — Phase 2 ships read, write, search and diffs, and leaves those to the user's IDE.
The tradeoff is that users who want an IDE will open their IDE, and h4rn will not compete there —
which is correct, because the product's value is orchestration, not editing. Reconsider LSP only
if the editor becomes a primary surface.

## ADR-014: React 19 + Vite + Tailwind v4 + shadcn/ui + `motion`; orbs and blobatars for state and identity

**Status:** Accepted

The UI is React 19 with Vite, Tailwind v4, shadcn/ui and `motion` (motion.dev). Agent state is
shown with **`thinking-orbs@0.3.2`** behind an h4rn-owned `<AgentGlyph state>` that owns the
mapping table, and the **`gravity` layer is disabled** — it is the only expensive path in the
package (blur filters, `getImageData`, per-frame sprite warp) and it needs per-platform cursor
rasters. Identity avatars use **`blobatar@2.7.0` + `@blobatar/react@2.7.0`**, pinned exactly,
with the type-prefixed seed scheme from the research (`machine:`, `harness:<machine>:<kind>`,
`subagent:<machine>:<parent>:<id>`, `thread:`, `user:`), static `<img>` in lists and
`animate="hover"` only where one avatar is the subject; `palette` is banned because it voids the
4.5:1 contrast guarantee. Transitions are 150–250 ms and every animation is disabled under
`prefers-reduced-motion` — both libraries already collapse to static frames, which is why they
were chosen. The tradeoff is two visual dependencies in the view layer and a WebKitGTK ≈2.42 floor
if animated blobatars are ever considered a designed behaviour on Linux.

## ADR-015: CLIProxyAPI is feature-detected, never version-detected

**Status:** Accepted

CLIProxyAPI is an optional upstream, integrated three ways: as a `base_url` for each harness using
the per-harness recipes (Anthropic base URL omits `/v1`, OpenAI includes it — a distinction encoded
as per-harness tests), as a pattern source for model-level credential cooldowns and three-format
`/v1/models` dispatch, and as an optional metering source. Capability is established by **probing**,
never by parsing a version: `HEAD /healthz` for liveness, a keyless `GET /v0/management/debug`
whose 401 carries `X-CPA-VERSION`/`X-CPA-COMMIT`/`X-CPA-SUPPORT-PLUGIN`, then authenticated route
probes (`/usage-queue`, `/v8/management/config`, `/v8/management/performance`). The reason is
concrete: the fork h4rn targets is based on `v8.0.47` and is **260 commits behind** upstream
`v8.0.69`, so "newer version means more features" is false, and vendors rebuild without bumping the
string. Each harness has its own enable toggle and env/config override, so users can route Claude
through the proxy while Codex stays direct. Usage comes from the fork's `/performance` or
`/usage-queue` **when present**, otherwise from h4rn's own self-metering of harness stream events;
`/usage-queue` is read-only to h4rn because CPA's own endpoint consumes what it returns. The
tradeoff is that h4rn must own metering, since CPA's history is in-memory and resets.

## ADR-016: Secrets in OS keychains, envelope-encrypted in Postgres

**Status:** Accepted

Client-side secrets live in the OS keychain via the `keyring` crate on desktop, and on mobile in
Android Keystore / iOS Keychain through the Tauri plugin. Server-side secrets — upstream
credentials, OIDC client secrets, forge tokens — are stored in Postgres as **XChaCha20-Poly1305**
envelopes under a key-encryption key supplied by configuration, never in plaintext and never in a
`.env` that doubles as the database password. T3 Code's model (DPoP keys in IndexedDB, hashed
pairing credentials) is right for pairing but insufficient for provider credentials, and
CLIProxyAPI demonstrates the cost of the alternative: its `/api-key-usage` response includes the
plaintext credential in the map key, so anyone with the management key has every upstream key.
Envelope encryption means a database dump is not a credential dump, and rotating the KEK is a
single re-wrap pass. The tradeoff is that the KEK must be available at relay boot (so it lives in
the deployment's secret manager, not in Postgres), and losing it is unrecoverable — documented as
such rather than silently falling back to plaintext.

## ADR-017: Cargo workspace + Bun workspace, Tauri v2 for both shells

**Status:** Accepted

The repository is one Cargo workspace (`h4rn-core`, `h4rn-protocol`, `h4rn-daemon`, `h4rn-harness`,
`h4rn-mcp`, `h4rn-transport`, `h4rn-connect`, `h4rn-vt`) and one Bun workspace for the UI, shared
tooling and generated bindings, with Tauri v2 providing both the desktop and the mobile shells.
Tauri v2 is chosen over Electron for the reasons the T3 research makes unavoidable: h4rn already
ships a Rust daemon, so the shell should not add a second runtime, a Node ABI surface, or a
`node-pty`-class native-addon rebuild problem — `portable-pty` and the daemon remove that whole
category. Tauri's mobile targets also make the "same UI on desktop, mobile and web" claim
achievable with one component tree, which Electron cannot. The tradeoff is that Tauri's WebView is
platform-specific (WebKitGTK on Linux, WKWebView, WebView2), so UI work must be tested against
three engines, and some Web APIs (notably around `@property` and background sockets) need floors
or fallbacks rather than assumptions.

## ADR-018: Self-hosted-first connect, with a configurable relay endpoint

**Status:** Proposed

h4rn-connect ships as a self-hostable axum + Postgres service with **no hosted default** and no
compiled-in relay URL; the client takes `H4RN_RELAY_URL` (or a per-account setting) and pairs
against whatever the user runs. This mirrors OrbitID, which has no hosted instance and no default
issuer, and it is the honest position for a product whose value proposition is "your daemon, your
machine, your credentials". A single-tenant mode (one relay, one team, pairing code printed by the
daemon) is the default deployment shape; multi-tenant hosting is a later, separate concern. The
tradeoff is onboarding friction — a user needs a reachable host and an IdP before remote access
works — which ADR-025 partially mitigates. The alternative, a hosted default, would put h4rn in the
position of operating the relay that sees every user's metadata, which the E2E design only
partially excuses.

## ADR-019: WSL and remote hosts are first-class daemon hosts

**Status:** Proposed

A daemon may run on Windows-native, WSL2, Linux, macOS, or a remote SSH box, and the UI treats the
host as an addressable environment rather than assuming "localhost". This requires host-scoped
path translation (`/mnt/c/...` vs `C:\...`, and never round-tripping a translated path back into a
prompt), a polling fallback for file watching where 9p/inotify is unavailable, and port discovery
attributed through `H4RN_THREAD_ID` because a port opened inside WSL is reachable from Windows but
not vice versa. The research makes this concrete: T3 Code already injects a thread id into every
agent shell so a listening port can be mapped back to a thread, and the Antigravity findings show
how often a harness writes to paths that only make sense on one host. The tradeoff is that path
handling becomes a daemon-wide concern with its own tests instead of a string concatenation, and
some features (native notifications, file pickers) must be explicitly degraded on hosts that
cannot provide them.

## ADR-020: The harness matrix is data, not code

**Status:** Proposed

The per-harness knowledge that T3 Code hard-codes across seven adapters becomes a declarative
`HarnessSpec` table: `{ transport, resume, approval model, interrupt, mcp mechanism and placement,
attachment capabilities, model listing, mode flags }`, with typed escape hatches for the cases
that genuinely differ. This is directly justified by the research's closing recommendation and by
the observable cost of the alternative: two adapter generations and a 13,733-line Claude adapter.
A table makes the differences reviewable in one place, makes a new harness mostly configuration
plus one protocol client, and makes the UI able to ask "can this harness accept an image?" without
knowing which harness it is. The tradeoff is that a bad abstraction forces awkward escape hatches,
so the rule is that the table carries only what the UI and the orchestrator must branch on, and
everything else stays inside the adapter.

## ADR-021: Process supervision is a first-class daemon responsibility

**Status:** Proposed

Every agent process is spawned into its own process group with a watchdog: a `/bin/sh` wrapper
that traps `TERM`, holds an inherited fd-3 liveness pipe owned only by the daemon, and on daemon
death sends `TERM` then `KILL` to the whole group; a 1 s `ps` sweep catches `setsid` descendants;
and on Linux each thread gets a cgroup v2 scope with `oom_score_adj=800` so an OOM kills the agent
rather than the daemon. This is copied from T3 Code because it is the only mechanism that
eliminates the orphaned-agent class of bug — the thing that leaves a `claude` process burning
tokens after the app crashed. The tradeoff is platform-specific code paths (cgroups are Linux-only,
process groups are not, Windows needs job objects), and a supervisor that must itself be simple
enough to be trustworthy. It is still cheaper than debugging why a user's machine has eleven
orphaned harnesses.

## ADR-022: Checkpoints are git objects, worktrees isolate threads

**Status:** Proposed

**Implementation note.** Subagent isolation ships today: `spawn_subagent` creates a worktree at
`<data_dir>/subagents/<id>/worktree` on branch `h4rn/sa-<short id>`, and removes it at
settlement. Top-level thread creation does not: `CreateThread` with `worktree` set returns
`NotImplemented`, so a new thread runs in the absolute `workspace_path` it was given. This ADR
stays Proposed until checkpoints and CreateThread worktrees land.

Before and after each turn the daemon writes a checkpoint as a git commit object under
`refs/h4rn/checkpoints/<scope>/<ordinal>`, built with a temporary index (`write-tree`,
`commit-tree -p HEAD`, `update-ref`) so the user's index and working tree are never touched, and
each concurrent thread may run in its own worktree. T3 Code's implementation is the reference and
its properties are exactly what h4rn needs: checkpoints are content-addressed, cheap, GC-able,
survive branch switches, and give the diff view a correct base without stashing. Worktree
isolation is what makes parallel agents safe on one repository, and it is also how "revert this
turn" becomes possible for harnesses that support it. The tradeoff is git plumbing that must be
bulletproof (a partial checkpoint is worse than none), plus disk growth and worktree cleanup when
a thread settles; both are handled by GC at settlement and by never checkpointing a dirty-tree
state the user did not create.

## ADR-023: Structured, redacted protocol diagnostics with replay fixtures

**Status:** Proposed

Every harness transport logs its native frames to a rotating NDJSON file with a structured envelope
(`{provider, protocol, kind, session, event}`) and key-based redaction of `authorization`,
`api_key`, `token`, `password` and `secret`. This is T3 Code's `EventNdjsonLogger` pattern, and it
is the difference between "the harness broke" and a reproducible bug: a replay test can replace
only the transport and feed the recorded frames back through the adapter. Vendor protocols are not
stable contracts (ADR-005's central risk), so diagnosability is a feature, not developer
convenience. The tradeoff is that the log contains prompts and file contents, so it must be
opt-in, local-only by default, size-bounded, and excluded from any support bundle unless the user
explicitly includes it; redaction is a deny-list over a schema that will drift, so a second pass
strips anything that looks like a bearer token.

## ADR-024: Metering is a durable append-only ledger, not a counter

**Status:** Proposed

h4rn records token and cost usage in an append-only ledger, one row per harness turn (and per
proxy call when CLIProxyAPI is in the path), keyed by thread, run, harness, model and credential,
with retention owned by h4rn rather than by a proxy. The CLIProxyAPI research exists mostly to
prove that the obvious source is not good enough: `/usage` was removed in 6.10.0 and was never
persisted, `/usage-queue` is destructive and goes permanently empty when a plugin subscribes,
`/api-key-usage` is counts-only with a 200-minute window, and per-credential counters reset on
restart. Only the fork's `/performance` has TPS data, with 7-day / 50,000-call retention. So
h4rn's own stream events are the system of record and CPA is an enrichment source. The tradeoff
is that self-metering can disagree with the provider's bill (stream events omit some cached-token
accounting), which is why the ledger stores the raw usage payload alongside the normalised numbers
and marks a reconciled total when a provider report is available.

## ADR-025: Generic OIDC, no OrbitID lock-in

**Status:** Proposed

h4rn-connect accepts **any** OIDC issuer that satisfies the discovery contract, with OrbitID's
quirks handled as a compatibility profile rather than as the only path, and an optional
single-tenant local-account mode for a solo deployment with no IdP. This follows directly from the
OrbitID finding that there is no hosted service and no default issuer anywhere in its docs or
image references, which means every h4rn user must otherwise stand up an IdP before pairing works.
Supporting generic issuers costs little because ADR-011 already discovers every endpoint, and it
removes the product's dependence on one project's release cadence (whose two builds already differ
on PKCE defaults, `form_post`, `end_session`, and id_token claims). The tradeoff is that quirks
must be capability-detected rather than assumed: PKCE, device grant, `form_post`, logout and access
token format are each probed from discovery or config, and a generic provider that lacks one of
them degrades instead of failing.

## ADR-026: Antigravity runs ACP-first with an explicit mode and no rewind

**Status:** Proposed

Antigravity is driven over `agy acp` with `--process-per-session`, an explicit `--mode`
(`plan` or `accept-edits`), client-enforced permissions, and `--sandbox`; `--dangerously-skip-permissions`
is never passed. `session/request_permission` is answered by h4rn, which is what makes "waiting for
approval" a real state rather than an unanswerable TTY prompt. The stream-json print mode is the
documented fallback and one-shot JSON serves utility calls, with `-p ""` always last because `-p`
otherwise swallows the next flag. Resume is always `--conversation <uuid>`, never `--continue`
(per-profile and racy), and `protocolVersion` is read from the reply (1.5.7 answers `1` to a `2`
request). The UI does not offer rewind or in-session compaction, both of which `agy` cannot do over
ACP, and any clean-tree or diff check allow-lists the empty `.gemini/skills` and `.agents/skills`
directories it creates at session start. The tradeoff is a deliberately smaller feature set for
this harness than for Claude/Codex, which is preferable to buttons that silently do nothing.

**Addendum: ACP normalization that the UI can trust.** `session/prompt` is only reported as
written once the client has flushed the frame to the agent's stdin; an interrupt therefore always
sends `session/cancel` after the prompt it cancels. Waiting for writer-queue space and waiting for
the flush share one ten-second deadline, and every other frame (cancel, model and mode changes,
approvals, notifications, `session/close`) waits under the same deadline; on expiry the writer task
is stopped and the agent killed, so a blocked frame cannot reach it later and a full queue cannot
stall Stop past that deadline. Replies the reader sends while answering the agent (`fs/*` responses,
permission answers) go through that same bounded queue, so a full writer queue cannot park the
reader either. Such a timeout ends the turn with exactly one failure row and detaches the dead
session, so the next message starts a fresh one; an agent the client killed itself does not publish
a second exit-error row, and a writer task that fails on an I/O error marks the client closed so the
daemon detaches it. A Stop belongs to one turn: a Stop that arrives before that turn's prompt is
dispatched, including while the session is still starting, ends the turn as interrupted without
writing anything, and a Stop for a turn that already ended does not cancel the turn that replaced
it. A thread starts at most one agent at a time: every startup carries a generation, so a startup
that returns after a restart or shutdown discards the session it made instead of attaching it, and
every detach names the generation it inspected so it cannot drop a session it never saw. Each turn
ends through one settlement, which publishes exactly one `TurnCompleted` (and at most one error row
for the losing side of a Stop-versus-failure race), promotes the next queued message to the active
turn under the same record lock so a later Send queues behind it, and leaves a late failure report
from an already-detached session out. Stop reasons are not flattened: only `end_turn` is a normal completion, `max_tokens` and
`max_turn_requests` end the turn as a visible early stop, `cancelled` is an interrupt, and a refusal
or an unknown reason is a failure. The interrupt flag belongs to one prompt: it is cleared when that
prompt takes the running slot and set only while it is running, so a late Stop (or a rejected second
send) cannot colour the next turn.
`tool_call_update` is merged into the tool row's last non-empty title, kind, input and locations, so
a status-only update never renames a tool or empties its expanded input, and the id is forgotten
once the call finishes.

**Addendum: one pump, one session.** Each event pump carries the generation of the session it
serves and drops every event once the record no longer holds that session live; every path that
detaches a session also aborts its pump. A late completion from a dead transport therefore cannot
settle the turn that replaced its own. The pump reads a session's transport health from a
lock-free flag the adapter publishes, never from the session lock: `send` may hold that lock for a
whole turn, waiting for a reply that only the pump's draining can deliver, so waiting on it there
would deadlock a harness with a bounded event queue. A startup that reached the thread after its
turn was stopped starts no session at all and leaves the slot free for the next message, and a
startup failure ends only the turn that startup captured; any turn that arrived later gets its own
startup attempt instead of a failure for a session it never asked for. A stream that ends while the
promoted turn's prompt was never written leaves that turn for a fresh session instead of failing
it. Error rows are tagged where the death happens: the ACP writer-error path, a closed or exited
agent, and a prompt that failed because the transport died report a distinct transport-death event,
and only those reports and the daemon's failed-write row for the same turn collapse into one row,
which keeps the agent's stderr text. Any other harness diagnostic is always its own row, so one
buffered before a death can no longer take the failure's place. A writer I/O error marks the client
closed and kills the agent's process group before any caller is woken, so an agent that closed
stdin cannot outlive the failure. A failover that arrives while a startup is still booting the old
model supersedes that startup, so the resume starts on the new model. A prompt result without a
string `stopReason` is a failure, never an implicit `end_turn`: ACP requires the field, and every
recorded turn end in `crates/h4rn-harness/tests/fixtures` sends it, so a reply that omits it is
malformed rather than a normal completion.

**Addendum: a startup's death is the turn's, and a death has one row.** A turn may move off the
previous turn's session once: if that agent exits while a promoted message is still waiting, the
message gets one fresh startup. But a session started for a turn is that turn's only attempt: if it
loses its event stream before its prompt is claimed, the turn fails ("the agent exited before it
accepted the prompt", with the agent's stderr when there is any) and the queue advances, instead of
a replacement session being started for the same turn forever. A transport death is often reported
more than once (the bridge's generic stdout-close notice, the prompt failure that carries the agent's
stderr, an exit row): the first report is held for the turn's settlement, later ones only sharpen its
detail, and the settlement publishes the most specific of them as the turn's one row, so the generic
notice can never hide the stderr. A frame the client's writer drops because the writer task exited
tears the transport down before the caller is woken, so a prompt error never leaves an open client
behind it. A writer that fails on an I/O error reports what the pipe said ("Broken pipe"), not just
that the writer exited, so the daemon's one failure row for the write names the real cause; when the
agent also left a diagnostic on stderr, the row keeps both. Detaching a dead session and settling the
turn it leaves behind happen under one record lock, so no delivery can see the empty slot and start
a replacement for a turn that is about to be marked failed. When the pump instead hands a still
pending turn to a fresh startup, the dead session's held transport report is dropped with it: the
retry must not inherit that session's death as its error row.

**Addendum: a failed startup clears and settles together, and a death waits for its report.** A
startup that fails clears the slot it owns and settles the turn it captured under one record lock,
so a second startup scheduled for the same turn runs either before that failure (and sees its
`Starting` slot) or after the turn has ended (and starts nothing); it can never take the empty slot
and write the prompt just before the failure is recorded. When stdout closes before the agent is
reaped, the prompt that wakes on the EOF waits up to 500 ms for the supervisor's exit report and the
stderr drain, then merges the exit status and the agent's last stderr line into the turn's one row.
A rate-limit reset that only the exit report carries still reaches the auto-resume schedule exactly
as an exit report on its own does. A writer that sees stdin close likewise waits for the stderr
reader to drain the pipe before it wakes the caller, so a diagnostic printed in the same step as the
close is part of the failure row.

**Addendum: a write deadline keeps the reset, and an idle death has one row.** A prompt that never
reaches an agent that stopped reading stdin fails on the write deadline, and that path collects the
same bounded stderr tail and exit report as a closed transport; a reset time printed there becomes
the typed limit, so the daemon persists the schedule and the message queued behind it waits instead
of running straight into the limit. A typed limit is rendered as the message alone under a
`Rate limited:` prefix rather than as a rejected write. Between turns the bridge reports the same
death twice as well (the generic close, then the exit status with the stderr it drained); those
reports are held per session generation and published as one row, so the exit status and the stderr
are never lost to the generic notice.

**Addendum: a death is published from its report, and the pump ends with its session.** A live
adapter keeps its event sender alive for as long as the daemon holds its session, so a session's
stream does not end when the agent dies: it only ends once the daemon drops the session. An idle
death therefore publishes its row as soon as the exit/status report for that generation arrives
(the generic stdout close alone gets a 500 ms window for that report, the same window a failed
prompt waits for), and the dead session is detached under the same record lock, so the next message
starts a fresh agent. A pump that settles a turn on a closed transport, or publishes an idle death,
detaches and shuts its session down, schedules any successor and then returns: it never waits for a
stream end the session it still holds keeps from happening. Every other detach (a Stop, a restart, a
model change, a failed prompt write, a shutdown) aborts the session's pump, so exactly one path
ends each pump. The `agy-fixture` peer gained the two deaths that happen outside a turn: an answer
followed by an exit, and an answer followed by a stopped stdin reader and a reset on stderr, which
the write deadline turns into a typed limit.

**Addendum: a completion on a closed transport waits for its exit report, and a death does not raise
a failure.** ACP can answer `end_turn` and only then exit, with the provider's reset on the exit
report rather than on the turn. The completion therefore gets the same 500 ms window for that
report that every other death gets, and a limit it carries is armed while the turn still owns the
record, before the completion detaches the session and promotes the queue; otherwise the queued
message would start at once on a fresh agent. A row published for a death between turns is a
diagnostic, not a failed turn: it never raises a failure, so a thread whose auto-resume just armed
stays Scheduled (as on main, where only the wire row was published). When several reports describe
one death, the exit/status report (`retryable: false`) always wins over the generic stdout-close
notice (`retryable: true`) even when its text is shorter, and only reports of the same kind are
compared by detail. The `agy-fixture` peer models both new orderings, plus a mid-turn exit with no
stderr at all.

**Addendum: a death names its end, and the restart, write and registration paths re-check.** A
transport death now says which part of the transport reported it (stdout EOF, a stdout read error, a
writer failure, or the process exit). Only the exit kind is the process's final account, so a read
error that is also non-retryable no longer ends the wait for the exit report's status, stderr and
rate-limit reset; both a completion on a closed transport and a death between turns keep waiting for
that kind. A `Write` report between turns is terminal instead: the writer's teardown kills the
process on purpose, so the adapter suppresses the exit report and no later event can sharpen or
contradict that row. Every non-deliberate exit publishes its exit report even when its stderr carries a typed
limit, so the limit arms auto-resume and the pump still learns that the session is dead and detaches
it; an idle death therefore reaches the next Send as a fresh session rather than as a failed write on
a dead one. Events buffered inside the exit-report window are applied to the completing turn before
it settles, and the idle fallback prefers a queued report over its deadline, so a tool update that
completed behind a closed completion is part of the turn it belongs to. Two ownership checks moved
under the lock they guard: a proxy restart re-checks that no turn became active under the same lock
as its detach and skips the thread when one did (the new routing applies on the next session start),
and an ACP request checks the closed state under the pending-map lock, so the reader's final drain
either drains it or registration rejects it instead of leaving a waiter behind. A prompt write that
lost its session to a restart, a shutdown or a model change puts its still-claimed prompt back and
delivers it on the live session or a fresh startup instead of returning with the turn Working. The
`agy-fixture` peer models the exit-only idle death by holding stdout open from a keeper process, so
no EOF can announce the death.

**Addendum: a Stop survives a lost session, and a buffered approval expires with its turn.** Stop is
recorded on the turn's dispatch even when the prompt is already claimed: if the session detaches
before the cancel can reach it, the failed write settles the turn interrupted instead of putting the
prompt back, so a Stop the person saw acknowledged never replays on a fresh session. The prompt path
now reports the close the client observed (stdout EOF, read error, writer failure or process exit)
rather than always calling a stdout close a write failure. Inside the closed-completion window an
approval that arrives behind the completion is dropped instead of published: it was never visible,
and the turn's settlement detaches the transport, so no session could ever receive an answer.
Finally, only the exit report ends that window, and it carries the provider reset itself: an ordinary
limit notification without a reset no longer ends the wait before the exit's reset arrives to arm
auto-resume.

**Addendum: a Stop that was not delivered is retried, and recovery is one decision.** A Stop records
its intent on a claimed turn so a failed write can never replay the prompt, but a cancel that failed
with the session still open is not a stop: every later Stop on that claimed turn tries the cancel
again, and only a cancel that had no session left (or a session already closed) counts as done.
Whether a prompt whose session detaches goes back to the queue or its stopped turn ends interrupted
is one operation under the dispatch lock. Split into a check and a later requeue, a Stop landing
between them made the requeue fail and returned without settling, leaving the turn Working with no
delivery; now the same interleaving either requeues or settles, never neither. Finally, the wait for
a closed transport's exit report prefers a ready report over its deadline, as the idle fallback does,
so a completion whose report and deadline are ready at the same poll keeps the exit's status, stderr
and rate-limit reset.

**Addendum: one provider limit arms one schedule, and a closed transport keeps the reason it died.**
Inside the closed-completion window the adapter can report one pause twice: the prompt path's typed
limit lands before the completion and the exit report carries the same reset after it. The window now
collects its limits and applies one after the wait, preferring the exit report's reset, and a limit
the turn already armed for that reset is never replaced: the schedule keeps its first attempt and
therefore its jitter instead of being silently bumped. A request rejected because the transport is
already closed now names the close the client observed (stdout EOF, a failed read, a writer failure
or the process exit) rather than always blaming a write, so the daemon's one failure row says what
actually ended the agent.

**Addendum: a cancelled resume stays cancelled, and a Stop outranks the death that follows it.** The
reset a turn already applied is kept on the turn's own record, not only in the live schedule, so the
exit report's repeat of that reset cannot arm a new schedule after the person cancelled the resume
while the report was still arriving; a different, newer reset still arms one. When a stopped turn's
session dies before the cancel can be delivered, the turn ends interrupted and the transport report
that arrives behind the Stop is dropped instead of becoming an error row: the person already ended
the turn, and a limit the report carried was applied on its own event. The generic stdout-close
notice also keeps the kind the reader observed, so a failed read is not reported as an EOF.

**Addendum: a dead reader leaves the slot, and a stopped turn's failed completion stays quiet.** An
idle session whose reader fails (a stdout read error or EOF) is detached from the thread's slot as
soon as that failure is known, not when the exit report finally arrives. The pump keeps the session
and its stream, because the exit report can still sharpen the one diagnostic row and carry the
provider's reset, but delivery no longer sees it: a message sent in that bounded window starts a
fresh agent instead of claiming a transport that can never take the prompt. The held report survives
the new turn that message starts, because it belongs to the dead generation rather than to that
turn. The exit report's reset is armed once, without replacing a schedule the adapter's typed limit
already armed for it. Separately, a turn the person stopped and whose ACP session then dies ends
interrupted, not failed, even when the adapter reports its `TurnCompleted{Failed}` after the cancel
closed the transport: the same rule the stream end already followed, with the death's report dropped
so it takes no error row.

**Addendum: every dying generation keeps its own death, and only a failed completion follows a Stop.**
Pending idle deaths are kept by session generation, not in one slot. The first dead session's
replacement can be started by a Send and die too before the first exit report arrives; each pump now
finalizes only its own generation, so both deaths publish their own row and their own reset instead
of the second overwriting the first. The reset a death already applied is likewise kept on that
death, so an exit report that repeats it cannot arm a new schedule after the person cancelled the
resume during the window, even though the live schedule is gone. Finally, the Stop override on a
closed-transport completion applies to a `Failed` report only: when ACP already reported the turn
`Completed`, a Stop that arrives while the exit report is still on its way leaves it completed — the
work was done, and the person's Stop never reached the agent.

**Addendum: a cancelled resume survives an exit-only death, and the newest pause wins.** The
bridge can report `LimitHit` and then `Exit` with the same reset with no EOF or read error in
between. The session is still live when the limit arms, so the slot itself now remembers the reset
that generation applied and hands it to the dying entry when the death is noticed; an exit-only
report that repeats it cannot re-arm the resume the person cancelled. When several dead generations
are waiting for their exit reports, a schedule records which generation armed it. An older
generation's later report, and a typed limit on its stream, keeps its own diagnostic row but never
replaces a schedule a newer generation armed, so the thread waits for the newest provider reset.
Finally, a failed write that lost its session and puts its prompt back still honors the adapter's
typed limit: it arms the schedule under the same lock, holds the requeued turn behind it, and the
schedule's firing delivers that turn (not the policy's resume prompt) on a fresh session. The
two-death test now holds the mocked clock until both exit reports have been delivered.

**Addendum: a paused requeued prompt is released by the person's action, and only its own session
owns the pause.** Clearing the schedule is a decision, not a state to leave a turn in: when the
person cancels the resume, or a Send supersedes the pause while the active turn's prompt is still
Pending, the parked turn is released for delivery (a Send's own message queues behind it and runs
second). Applied resets are recorded only on the session generation that reported them, so an older
generation's delayed exit cannot consume the live replacement's own reset; a requeued write's pause
names the generation that claimed the write rather than an empty slot. A newer generation that
confirms the same reset takes ownership of the existing pause without changing its attempt or jitter,
so an older generation's delayed earlier reset cannot replace it. A fire re-checks the schedule's
identity on the record under the record lock before it clears the pause or hands off delivery; if a
newer limit replaced it while the attempt was claimed, the old fire does nothing. Finally, a typed
limit without a reset time on the requeued-write path waits the meter's unknown-reset backoff like
any other reset-less limit instead of retrying at once.

**Addendum: a release never waits on storage, and a pause parks only its own prompt.** Releasing a
parked prompt is a state decision the person made, so it cannot depend on a write landing: the
schedule's firing claims its attempt (which is what makes it unfireable again) and then delivers the
pending turn whether or not the ledger records the outcome, and `Send` and `CancelResume` deliver the
turn they release whatever the journal says, logging the failure. The thread is projected as running
on release by its own lifecycle event, which clears the paused phase and the limit without counting a
turn: a cancelled or superseded pause shows the thread Working, not Rate limited with a resume time.
A fire acts only when the record names the schedule it claimed (the ledger id restored from the
ledger for a schedule the daemon inherited), because a missing pause proves nothing about the attempt
that was claimed; the failover model change and its session detach happen after that check. A pause
records the dispatch it parks, so only that requeued prompt waits: an old generation's exit report
arming a pause while a Send starts a replacement leaves the replacement to start exactly as it does
on main. Applied resets carry their session generation on the turn and the live slot, and a live
session that adopts an equal reset (ownership transfer) records it for its own generation, so a
cancelled resume is not re-armed by that generation's exit-only repeat. The parked prompt itself is
stored on the thread row: the journal is restored before the ledger is attached, so a restarted
daemon rebuilds the dispatch and its pause (naming the restored turn), and the schedule's firing
delivers the person's prompt rather than the policy's resume prompt. If the schedule did not survive,
the restoration releases the turn instead of leaving it pending. The tests that cover these paths use
the fake harness's session/send notifications, a start gate and a held clock, and the storage-failure
and restart paths run on a journal and ledger that are deliberately broken or reopened.

**Addendum: a reply in the pipe survives the exit, and a promoted turn waits for the exit report or
is handed back to its pause.** A message queued behind a turn is the daemon's own next step, not the
person's Send, so it is marked as promoted when the settlement moves it out of the queue. A real ACP
peer answers `end_turn` with an ordinary newline-terminated frame and then exits at once, so the
process can be reaped while the reply is still in the pipe. The supervisor therefore waits, bounded,
for the stdout reader to reach EOF before it fails anything still pending: the reader resolves every
reply the agent wrote, and only requests with no answer are failed with the exit report. The adapter
also publishes a turn's settlement through the reader's own event queue, so it lands behind every
update the reader had already taken, and the bridge drops a `session/update` that arrives after a
settlement until the next prompt starts: a finished turn's text can no longer be applied to the turn
that follows it, and it can no longer make a turn that never ran look as if it produced output. Two
rules keep the pause authoritative. A death observed between turns (the close arrives while no turn
is active) opens the bounded exit-report window, and the queue's promotion waits for it: it does not
start an agent, and the publish path advances the queue once the verdict is in. In the ordering the
fixture forces, the completion is published while the transport is still open, so that wait does not
apply; the promoted write fails on the dead pipe instead, and the turn is handed back to the queue
rather than failed. Its prompt never reached the provider, so nothing it collected can be its own,
and the armed schedule names it and delivers it after the reset. Only the write-failure path may
requeue without the quiet check for that reason; a promoted turn whose own completion failed on a
closed transport may go back only when the harness never accepted its prompt. Acceptance means the
harness accepted the write; for ACP that is a successful flush of the prompt frame, not proof the
agent read it. Because the prompt may already have been acted on (an edit it never reported), such a
turn settles as limited with its trace and the person can resend it; it is never run again
automatically. A Stop that lands while a closed session's write fails settles the turn Interrupted
with no transport row, exactly as a Stop on a detached session does. A paused prompt with no
schedule that can be armed (no usage meter, or a ledger that refuses it) is failed honestly instead
of being parked with no delivery owner. A prompt is saved on the thread row only once a schedule
really owns it, including the failed-write requeue: the ledger's refusal leaves no orphan prompt for
a restart to deliver. The `agy-fixture` peer keeps its replies ordinary (a newline terminator, as a
real peer writes them): `H4RN_FIXTURE_LIMIT_EXIT_AFTER_TURN` answers and exits at once with the
reset on stderr, and `H4RN_FIXTURE_LIMIT_EXIT_AFTER_QUEUE` keeps the transport healthy until the
promoted prompt reaches it, so the promotion-before-the-limit order is fixed by the test, not by the
machine.

**Addendum: work already done is never replayed, and a pause always owns its prompt.** Three rules
refine the requeue. First, "produced nothing" is read from a turn-long marker, not from the running
tool map: a *completed* tool call leaves that map empty, and it is the strongest proof the prompt
reached the provider's work, so such a turn settles as limited with its tool card and output and is
never written again. Second, ownership of a stream is established before a delta is published. The
ACP adapter tags every `session/update` with the prompt generation it follows and the bridge only
applies updates for the running generation. The daemon also holds a promoted turn's text, tools,
plan and usage from the moment its prompt goes on the wire (`on_the_wire`) until that write returns
`Ok`, and drops them when it fails: an adapter that has not accepted the prompt yet can still be
draining the finished turn's output, so those events are neither published nor journaled under a
turn whose write can fail and send the prompt back to the queue. Releasing in the adapter's order on
success keeps the turn's own first words. Only lifecycle reports are uncapped - a completion, a
usage limit, a transport close (the exit and status report), an approval and a session-started
report - and they are never dropped, or the turn would stay active forever. Everything else counts
against the hold's bound, including the diagnostic error the bridge makes from an unparseable
stdout line; like text, an error past the bound is dropped, so an agent that floods garbage during
the write cannot grow the hold without limit. An acceptance that lands between the hold's check and
the next event releases the held output before that event is applied, so output read first is
published first. ACP carries no turn id, so text a peer writes after it has read the new prompt is still
indistinguishable from the new turn's own output; the hold covers exactly everything up to the
acceptance. Third, a pause and its prompt are one record. The schedule binds to a turn only through
`parked_turn_to_keep`, and the prompt is saved on the thread row only when the ledger really armed
the schedule, in the same step, so a limit landing between promotion and claim survives a restart.
A ledger that refuses the schedule leaves no prompt on the row for a restart to deliver again. A
claim re-checks pause ownership under the record lock and refuses to write a prompt the pause now
owns. A requeue keeps the dead session's exit status and stderr row instead of clearing it, and the
published `auto_resume` flag is derived from the schedule that was actually armed: a limit that no
meter or ledger could schedule reads as rate-limited, never as `Scheduled`. Reply resolution is
independent of event delivery for the same "never lose the person's answer" reason: the reader
publishes into its own queue drained by one forwarder, so a full session queue can no longer park it
before the reply behind those updates. That queue is bounded at four session queues for every
non-settlement event - a session update, an unknown notification and an unparseable frame's error
are counted alike - and the newest is dropped and counted when it overflows. Permission requests
have their own small bound, and a request past it is answered at once with the cancelled outcome
rather than left unanswered; the terminal reports (`TransportClosed`, `Closed` and `Exited`) take
a third queue that is never counted or dropped, so a permission backlog can never delay an exit.
Under pressure a reserved event takes the next slot; with room the three lanes are merged by the
arrival sequence `publish` assigns, so a permission request that arrived before an update is not
overtaken and a close never overtakes the words read before it. A settlement stays in the ordinary
order, behind the updates the reader had already taken.

## ADR-027: Push notifications are metadata-only wake signals

**Status:** Proposed

Mobile push goes through h4rn-connect to APNs/FCM as a **wake signal only**: the payload contains a
thread id and a coarse state change, never a prompt, a file path, a diff, or a token. The app
wakes, reconnects over the normal multipath transport, and resumes by sequence number. This is
forced by ADR-010 — the relay cannot read the encrypted session, so it cannot compose a meaningful
payload — and it is also the correct privacy default, since push payloads transit Apple's and
Google's infrastructure. T3 Code pushes richer APNs/Live-Activity payloads, but it has no E2E layer
and can afford to. The tradeoff is a notification that says "a thread needs you" rather than what
it needs, and a cold-start path that must fetch state before showing anything; both are acceptable
compared with leaking thread titles to two more vendors.

## ADR-028: DPoP proofs carry a per-request nonce

**Status:** Accepted

Every authenticated REST request and every `/relay` upgrade signs
`h4rn-dpop-v1\nMETHOD\nPATH\nTIMESTAMP\nNONCE` with the device's Ed25519 key and sends the
signature, timestamp and nonce in `x-h4rn-proof`, `x-h4rn-timestamp` and `x-h4rn-nonce`. The
relay checks the key against the device record, enforces a timestamp window, and records the
signature in a replay cache. The nonce is load-bearing: Ed25519 is deterministic, so without
it two identical requests to the same path in the same second produce the same signature and
the second is rejected as a replay. That would break polling and retries, not just attackers.
The tradeoff is one more header and 16 random bytes per request; the alternative — server
nonces — adds a round trip or shared state, and omitting replay protection gives up sender
binding. The cache is per process, so a multi-instance deployment needs a shared store for
the strict single-use guarantee; the timestamp window still bounds cross-instance replay to
a minute, and this is documented rather than assumed.

## ADR-029: Runtime-checked `sqlx` queries, with Docker-backed integration tests as the gate

**Status:** Accepted

ADR-012 promised checked-in offline query metadata (`cargo sqlx prepare`) so CI could compile
without a database. This environment has no `sqlx-cli`, and checking in metadata generated by
a different schema is worse than not checking it in. `h4rn-connect` therefore uses
runtime-checked `sqlx::query_as`/`query` with `FromRow`, applies embedded migrations at boot,
and makes `scripts/test-connect.sh` (real `postgres:17` in Docker plus the real router) the
merge gate for schema and query correctness. `cargo test --workspace` stays hermetic; the
Postgres tests are `#[ignore]`d and the script runs them with `--ignored`. The tradeoff is
that a typo in a column name is caught by integration tests instead of the compiler, and the
suite needs Docker. Revisit by adding `cargo sqlx prepare` in CI once the tool is available;
the runtime-checked code needs no rewrite for that.

## ADR-030: Pairing claims are same-user, and the relay injects the authenticated device id

**Status:** Accepted

A pairing QR (`h4rn://pair?c=…&m=…&k=…&s=…&e=…`) is created only by the machine's daemon or
another device of the machine's owner, stores only a BLAKE3 digest of the one-time secret,
expires after five minutes and is single-use. Claiming it requires an authenticated device
belonging to the **same user** as the machine; a different user gets `machine_forbidden`, not
a generic bad request, because "someone else's machine" is an authorization failure and
leaking whether the QR was valid is unnecessary. The claim transaction links the device to
the machine, records the device's Noise static key, burns the secret, writes an audit entry
and tells the daemon over the relay. Clients never send a device id in `RelayOpen`: the relay
injects the authenticated id, so a peer cannot open a connection as another device. The
tradeoff is that a household with two accounts cannot share a machine through one QR; that is
a deliberate product boundary and a future explicit share grant can change it.

## ADR-031: One Noise `IK` handshake per path, pinned daemon key and device allowlist

**Status:** Accepted

Every candidate path runs its own `Noise_IK_25519_ChaChaPoly_BLAKE2s` (or
`IKpsk2` when pairing) handshake, bound to the logical session id in the
prologue. The device's X25519 static key is its identity in a persistent
allowlist, the Ed25519 key is kept beside it for device events, and the daemon's
X25519 public key is pinned from the pairing payload. A one-time PSK makes the
first handshake mutually authenticating, which is the only moment a new device
can enter the allowlist; after that the device drops the PSK and proves
membership with `IK`. Revocation removes the device key and returns an explicit
`revoked` reason before any session exists. The tradeoff is a handshake per
path (three instead of one), but it lets a path be added or replaced without
exposing the session to a new trust decision, and it keeps the relay unable to
join two paths under one connection. Rekeying is Noise's own rekey after a
message/byte budget, not a new identity or a new session.

## ADR-032: The session layer owns reliability and resume, not the socket

**Status:** Accepted

Sequence numbers, cumulative and selective acknowledgements, retransmission,
fragmentation and reassembly live in a path-independent session layer. Sockets
only carry packets. An `Open`/`Welcome` control exchange binds each fresh Noise
channel to the logical session and carries an opaque resume token, so a client
that reconnects or moves from LAN to relay keeps the same sequence space and
the daemon can retransmit exactly what was lost. Retransmissions are always
freshly sealed with the next Noise nonce but keep their original session
sequence and message id; the receiver deduplicates on sequence, never on
ciphertext. The tradeoff is a bounded retransmit buffer and reassembly window
(1024 records / 16 MiB by default) and backpressure instead of unbounded
memory, which is the correct failure mode for a transport that must not lose a
prompt. A daemon keeps a detached session for a grace period; after that the
resume token is dead and the application protocol's own `since_seq` replay is
the recovery path.

## ADR-033: wasm owns the crypto, JavaScript owns sockets and timers

**Status:** Accepted

The Noise handshake, key storage in memory, record sealing, session state and
path selection run in `h4rn-transport-wasm`; the TypeScript `SecureTransport`
only creates one WebSocket per candidate and ticks the core every 50 ms. The
same synchronous, clock-injected core powers the native async client, so browser
and native code cannot drift on protocol behaviour. TypeScript parses no key
material and implements no cryptographic primitive; it moves opaque encoded
identities and resume tokens between wasm and `localStorage`. The wasm target
needs `uuid`'s `js` feature, `getrandom`'s `wasm_js` backend and snow without
its `ring` default resolver; keeping those in the wasm crate avoids pulling
browser-only features into the daemon. The tradeoff is a wasm build step and a
second adapter to keep compiling, which is cheaper than two implementations of
a state machine where a one-byte divergence is a security bug.

## ADR-034: Skills are content-addressed bundles, installed as marked copies

**Status:** Accepted

A skill is a directory with a `SKILL.md` entry point plus references, scripts and assets. The daemon canonicalises it into a manifest of relative paths, sizes, BLAKE3 digests and executable bits, and derives the version id from a BLAKE3 digest of that manifest encoded as canonical JSON. Absolute paths, mtimes and owners never enter the hash, so importing the same directory on two machines produces one version id. Bundles are stored once under `skills/bundles/<version>`; SQLite (`skills/registry.db`) holds names, sources, revisions, install rows and conflicts. The registry is per user and per daemon data directory.

All four harnesses read a native `SKILL.md` directory, so there is no instructions-file fallback: Claude Code (`~/.claude/skills`), Codex (`$CODEX_HOME/skills`, default `~/.codex/skills`), OpenCode (`$XDG_CONFIG_HOME/opencode/skills`, default `~/.config/opencode/skills`) and Antigravity (`~/.gemini/config/skills`). Project roots are recorded for the UI but installs target the user root, the only path every harness reads without a workspace trust decision.

Installs are copies, not symlinks, because the `.h4rn-managed` marker must travel with the copy and because Codex and Antigravity share `.agents/skills` as a project root. The marker records the owner, registry id, name, version, harness list and install time. A directory without a marker is user-owned and is never overwritten, updated or removed; uninstall removes only a matching managed copy and narrows the marker when another harness still owns the shared directory. The tradeoff is duplicated bytes across harnesses, which is small for documents and scripts and buys a single ownership rule the UI can explain.

## ADR-035: Connect is a sync mailbox; the registry decides causality

**Status:** Accepted

Skill sync reuses h4rn-connect as a per-user mailbox, not as an authority. Each push carries the full bundle and a Lamport-style version vector keyed by the registry's stable machine id. The registry's monotonic `revision` is that machine's clock, so two machines cannot silently reuse a counter. Bundles are validated (`SkillBundle::from_wire`) and must hash to the advertised version before the relay stores anything; the relay never decrypts them.

Rows are envelope-encrypted at rest with the connect KEK and an AAD binding `user_id`, `skill_id` and `version`. Metadata (name, description, version, vector, ETag) stays plaintext so the relay can compare causality without reading skill contents. A push uses the server's stored vector: a dominating incoming vector wins, a dominated incoming vector is rejected with a conflict row, and concurrent vectors use `updated_at` as last-writer-wins while recording a conflict on the relay. A daemon whose push is rejected also records a local conflict pointing at its still-stored losing bundle, so the user can restore it; the winner has no equivalent local candidate and keeps the relay-side conflict row. The server returns an opaque cursor derived from a per-user sequence assigned at commit under a clock-row lock; a pull returns rows after that cursor, including tombstones. The sequence cannot be overtaken by a concurrent push that started earlier but commits later, so a pull never resumes past an entry it has not seen. Conflicts are visible until the user resolves one by keeping local, keeping remote or keeping both (the last renames the candidate).

Before the first byte leaves the machine the daemon scans the exact bundle for private keys, cloud and provider tokens, JWTs and credential assignments. A finding blocks the sync with `Blocked` state and a file/line hint; it is a successful, visible refusal rather than a transport error. The tradeoff is a deliberately noisy scanner and a relay that stores opaque bytes, which is the correct bias for a feature whose whole purpose is moving text between machines.

## ADR-036: MCP is implemented in-tree, with `server__tool` names and deterministic collisions

**Status:** Accepted

`h4rn-mcp` implements the MCP streamable-HTTP, stdio and legacy-SSE transports directly on
`axum`, `reqwest` and `tokio` rather than depending on an SDK. The hub needs control the general
purpose `rmcp` surface does not expose at this revision: per-session bearer tokens with scopes,
per-server enable matrices, a single reserved `h4rn` namespace shared with in-process providers,
owner-enforced share policies, deterministic collision renaming and redacted diagnostics. The
protocol is small (initialize, tools, resources, prompts, list-changed, cancellation), so owning
it costs less than adapting every one of those policies to an external type model. Names are
`server__tool`, server names are lowercased and normalised, `h4rn` is reserved, and collisions
get `_2`, `_3` in sorted-namespace order so the same configuration always exposes the same names.
The tradeoff is that new MCP revisions are our work; `negotiate_protocol_version` keeps the
accepted list explicit and tests pin the handshake.

**Amendment (council round 2).** Approval requests ride the same transient MCP event stream as
server status and tool-call audits (`McpShareApprovalRequested` / `McpShareApprovalResolved`), so
the UI has one forwarder and one reconnect story rather than a second notification channel. The
pending set is also readable on demand; nothing about an approval is durable, so a restart denies
waiting calls.

## ADR-037: MCP configuration and secrets live apart; sharing is owner-executed

**Status:** Accepted

The MCP registry is a separate `mcp.db` in the daemon data directory. It stores transports,
enable matrices, imports, shares and only *references* to secret values
(`mcp/<server id>/<kind>/<NAME>`); values go through the `SecretStore` trait into the OS keychain,
with an encrypted file fallback for headless hosts. The registry never sees a plaintext value, so
a copied database, a log line, a protocol view or a `Debug` format cannot leak one — the same
boundary ADR-016 sets for other credentials. Cross-machine sharing follows the same rule: the
owning machine executes the server and keeps the secret, a second secure session on
`/secure-mcp` carries JSON-RPC, and the owner re-checks the share policy and audits every call
with the authenticated device key. A proxy cannot be re-shared, so a chain cannot be used to
launder access. The tradeoff is one extra encrypted hop for remote calls and the need to clean up
secret references on update and removal; both are covered by tests.

**Amendment (council round 2, F1–F3).** The tunnel now has three path kinds ranked direct,
tailnet and relay, so two machines with no shared LAN or tailnet still share servers. The relay
frame carries an explicit `service`; daemon-initiated sessions use a peer-only `secure_mcp` route,
and connect admits them only within one account, never to the caller's own machine.
`confirm_all` / `confirm_tools` no longer deny unconditionally: the owner's daemon raises a
pending approval (tool name plus bounded argument preview), answered with the `approve` scope,
expiring closed after two minutes and cancelled when the tunnel drops. `allowed_devices` compares
the connect device id recorded on the peer daemon's host entry, which is why that id is carried
from peer discovery into `register_host`.

**Amendment (council round 4).** The tunnel guard runs before every protected operation, not only
`tools/call`: `tools/list`, `resources/list`/`read` and `prompts/list`/`get`
re-check the authenticated peer, the current grant and `allowed_devices` on each request, so
unsharing, narrowing the policy or restricting devices reaches a tunnel that is already open.
Tool-specific policy and approval checks stay in the shared call path. Peer admission is decided
from the registry rather than the in-memory set: a peer is skipped only when a `host` entry exists
for its key and the transport already allows it, and a failed `register_host` write is retried
with bounded backoff instead of leaving the peer unadmitted for the rest of the run. A `client`
key is still never re-roled.

**Amendment (council round 5).** Three follow-ups tightened the same areas. Pattern selection is
per device: while a one-time PSK is armed the daemon first reads message 1 with a plain `IK`
responder and replays it through `IKpsk2` only when that cannot use it, so an allowlisted device
keeps connecting with plain `IK` and the secret is consumed only by a new device that actually
pairs; a client holding a resume ticket never sends the PSK. A failed peer admission no longer
waits for another topology report: the retry driver re-applies the last merged peer set on its
own backoff timer and stops arming the timer when nothing is pending. The tunnel's `initialize`
now advertises `resources.subscribe: false`, matching the fact that the tunnel has no
`resources/subscribe` method; the earlier docs claimed that operation was guarded.

**Amendment (council round 6).** `IKpsk2` mixes the PSK only into the responder's message 2, so
message 1 cannot prove possession and round 5 let a wrong secret allowlist the key and burn the
real one. A PSK-authorised new device is now provisional: nothing is consumed, allowed or hooked
at message 1 or handshake completion. Possession is proven by the first transport record
decrypting under the PSK-derived keys; only then does the daemon consume the secret, run the
pairing hook and allow the device, before any `Welcome` or ticket. The initiator always opens
with plain `IK` and falls back to `IKpsk2` once, after a `NotPaired` reject, so a device that
lost its ticket after being admitted no longer retries a consumed secret forever. The policy is
re-read after the handshake so a mid-handshake revoke is honoured.

## ADR-038: A subagent is a child thread, not a second session type

**Status:** Accepted

Delegation creates an ordinary h4rn thread with `parent_thread_id` set, rather
than a parallel "task" object with its own lifecycle. That reuses everything
threads already do — durable event journal and replay, resume ids, usage
accounting, approvals, the harness registry, worktree-safe workspaces and the
MCP hub — and makes the child openable in the same conversation UI as any other
thread. The deltas are small and explicit: two metadata columns
(`parent_thread_id`, `subagent_id`), a `Delegated` item and spawn/finish events
on the parent, child rows hidden from top-level listings, and approvals mirrored
from the child onto the parent as `sa:<id>` with the child's `SubagentId` in the
event. A pre-allocated child id lets the supervisor record a spawn before the
first harness event can race past it. The tradeoff is that a subagent inherits
thread semantics wholesale (it can have many turns, its own inbox row and its own
resume id), which is exactly the property that lets a child run on a different
harness without inventing a second state machine.

## ADR-039: Delegation policy is enforced by the daemon, not the parent

**Status:** Accepted

`spawn_subagent` is a tool call from a model, so nothing it supplies is trusted.
The daemon independently validates the harness against its installed catalog,
derives nesting depth from persisted parent links (default maximum 2), rejects
zero or malformed budgets, confines `context.files` to the parent workspace
under a 128 KiB cap, and accepts only the local host in this phase. Every child
gets turn, wall-clock and token caps; omitted fields take daemon defaults rather
than meaning unlimited, because an unbounded delegation loop is the failure mode
that matters. The supervisor watches the child's journal, interrupts the harness
when a cap is exceeded, records `BudgetExceeded` (distinct from `Cancelled`) and
folds the terminal turn into a bounded `SubagentResult`. Worktree isolation lives
under the daemon data directory, and cleanup is state-dependent: keep the branch
on success, delete it on cancel or budget overrun. The parent's MCP token scopes
every operation to its own thread, so a token cannot read or cancel another
thread's children. The tradeoff is that policy lives in one daemon-side module
with no per-call escape hatch; a caller that needs a different bound must ask
for it explicitly and still pass validation.

## ADR-040: Quiet native UI direction replaces Prompt Book

**Status:** Accepted

The interface is the "Quiet native" direction: graphite neutrals at 260°, one 258° blue
accent reserved for "you" (needs-you dots, the primary answer action, focus and selection),
Geist/Geist Mono type, hairline panes, and platform-native navigation (sidebar, list, detail,
inspector, tabs, sheets). The earlier Prompt Book metaphor — cue gutter, numbered turns,
stage-black rail and status bar, amber attention bands, pill provenance rows, an orange logo
block, theatre vocabulary (cue/standby/strike) — is an anti-reference and no part of it
survives in the shell or the token layer. Product truth is unchanged: the Working / Done /
Settled lifecycle, host provenance, host-local secrets, reversible actions, honest harness
differences and the state vocabulary in `docs/ux.md` all carry over.

The change is forced by the usability finding that the metaphor added a translation step
between the user and the state words the product already uses: an operator had to read the
stage-manager costume before reading the work, and amber bars plus numbered rows made every
thread look urgent. The Quiet-native grammar makes attention a sorting tool: anything blue is
the user's, everything the agents do on their own stays neutral. It also lets the desktop and
phone use the patterns their platforms already teach, so density can rise where the operator
is competent (lists, tables, trees, tool rows) while decision points (approvals, consent,
resume) keep whitespace.

Consequences: `DESIGN.md` now records this direction as the adopted token/type/component spec;
`apps/ui` implements it through `tokens.css` and the `q-` layer; the terminal follows the
theme; the sidebar hosts group collapses past six hosts. The tradeoff is that the old
look's strongest brand signal (the stage silhouette) is gone, so identity must come from
restraint, the blobatar/orb system and typographic precision. Surfaces whose wire protocol
has not landed yet (Pull requests, MCP & skills, Usage, Settings, pairing) ship as clearly
marked mock-mode shells rather than as partial implementations.

## ADR-041: One platform secret store; browser storage never holds a credential

**Status:** Accepted

Every credential the view touches goes through `apps/ui/src/lib/platform/secrets.ts`.
On Tauri mobile it is the Android Keystore / iOS Keychain behind `secret_get`,
`secret_set` and `secret_delete`; on Tauri desktop it is the OS keychain behind
`keychain_get`, `keychain_set` and `keychain_delete` with service `h4rn` and the logical key as
the account. The web has no OS keychain, so it stores AES-GCM envelopes in IndexedDB
(`h4rn-secrets`) under a non-extractable `CryptoKey` kept in the same database. If IndexedDB or
WebCrypto is unavailable the page falls back to an in-memory cache for that page load rather
than writing plaintext anywhere.

The values covered are the daemon token, the pairing URI (including its one-time PSK), the
Noise identity, the pinned daemon key, the pending/session resume state, and h4rn-connect
access and refresh tokens. `localStorage` and `sessionStorage` never see them. Reads are
asynchronous but `prepareSecrets()` runs once before React mounts, so the few synchronous boot
reads (`readBootConfig`, `hasStoredSecurity`) answer from an in-memory cache and the rest of the
app uses `getSecret`/`setSecret`.

Existing builds left some of these in `localStorage` (`h4rn.token`, `h4rn.pairing`, any
`h4rn.secure.*`, `h4rn.remote.credentials`), in `sessionStorage`
(`h4rn.remote.credentials`) and, on desktop, in the old `h4rn-connect` keychain service. Boot
migrates each value into the new store, deletes the old copy, and only then continues. `?token=`
and `?pair=` bootstrap values are ingested the same way and stripped from the address bar, so
they cannot leak through history, screenshots or a copied link.

`sessionStorage` is still used for two things that are deliberately not secrets: the OIDC
`state`/redirect metadata for one tab, and nothing else. When the IDB record outlives a profile
reset, its envelope simply fails to decrypt and is skipped; a re-pair is required.

Why not memory-only on the web: the OIDC redirect leaves the page and returns through
`/auth/callback`, which would drop the daemon token and pairing PSK held only in memory.
The encrypted IndexedDB record survives that round trip; the cost is the same-origin caveat below.

Consequences: the daemon token survives reloads and relaunches on every shell without plaintext
storage; the web's at-rest protection is weaker than an OS keychain because same-origin script
can ask the page to decrypt, which `docs/transport.md` records in the threat model. Desktop and
mobile keep their native keychain implementations; the missing piece was a single interface and
a web backend, not another platform backend.

## ADR-042: Pairing scopes and a typed short code

**Status:** Accepted

A pairing used to make an all-powerful device and showed a fake code. Now it
grants a set of scopes (`view`, `approve`, `terminal`, `files`, `admin`; `view`
is implied) chosen when the pairing is created. `h4rn-connect` stores them on
`pairings` and copies them to `machine_devices` on claim (migration 0005; old
links keep all five), signs them into the device's access token as `scp`, and
includes them in the daemon's relay snapshot and `DevicePaired` event. Two places
enforce them. The relay API reads the live scopes from the database: creating or
revoking pairings and revoking another device need `admin`, and an unpaired phone
holds `view` alone. The daemon classifies every `ClientRequest`
(`required_scope()`, an exhaustive match so new requests must be classified) and
refuses with `forbidden` before dispatch. A re-pairing replaces the scopes. Local
(loopback) sessions are unrestricted; nothing else is.

The short code is 8 Crockford base32 characters (40 bits from the OS RNG), stored
only as a domain-separated BLAKE3 hash under a unique index over pending rows,
single use, expiring with the QR. At 40 bits the hash does not protect it; the
five-minute life, single use and rate limits do (10 attempts per user and per IP
per hour, charged hit or miss; another account's code is indistinguishable from
an unknown one). Trade-off: a typed code has no QR to pin the daemon's Noise key,
so the relay supplies it at claim and the first handshake trusts the relay for
it. The QR path is unchanged and remains the stronger one.

### Round-1 council amendments

**The daemon's device registry is the only authority.** `<data_dir>/devices.json`
(encrypted at rest) records, per Noise key, a role (`client` with scopes, or `host`
for a peer daemon), a provenance (`connect` or `direct`) and the connect device id.
Missing authorisation is denial: a key that completes the handshake but has no
entry gets `forbidden` on its first request, and a corrupt file means everyone
pairs again, never an open daemon. The session's identity is always the key the
handshake authenticated; a device id the relay puts in its `open` frame is a claim
and is replaced by the registry's answer. The registry is rebuilt into the
transport allowlist at start; keys in the old allowlist file but not in the
registry are not admitted. A relay snapshot is authoritative for `connect`
entries: absent ones are removed, their sessions terminated and the registry
persisted. Direct pairings are recorded with the scopes armed in
`direct-pairing.json` (`h4rnd pair --direct --scope …`; no `--scope` grants
`view` and `approve`) and survive snapshots. Binary frames are authorised like requests: PTY
input needs `Hello`, the `terminal` scope and a viewer this connection attached.
`SetThreadTab` and `Snooze` mutate state and need `approve`. The one-time PSK is
consumed atomically when the device is authorised, so racing handshakes pair one
device per QR.

**Typed-code pairing is confirmed by a short authentication string.** The relay
supplies the daemon's key for a typed code, so a malicious relay could sit in the
middle of the first session. The phone therefore stops after the claim: it derives
`short_auth_string(own key, daemon key as received)` in Rust (wasm export
`pairing_sas`) and shows it; the daemon derives the same function from the device
key connect gave it and its own key, and lists it under Settings → Devices
(`PairingConfirmations`, `admin`). Nothing is pinned until the person taps "They
match"; "They differ" revokes the device and signs it out. A swapped key on either
side makes the two strings differ. It is 12 digits (about 40 bits), not 6: a short
string can be ground in real time by generating key pairs until two strings
collide. Both paths show the phone the same comparison: for a typed code the
string is derived from the key connect supplied, and for a QR from the key the
code pinned out of band, so a relay substitution makes the two screens differ.
The host-side confirmation is the admission gate (see the round-2 amendment);
the phone's own confirmation pins the key it will trust (see the round-3
amendment). Limits: a pairing claimed while the daemon is offline queues no
confirmation until the relay snapshot arrives.

**Scopes are per machine.** `h4rn-connect` authorises machine-scoped actions
(creating or revoking a pairing, revoking another device) against the link's
scopes for that machine (`machine_scopes`), never the union across machines. A
machine's own daemon holds every scope on its machine. A device linked only to
other machines holds nothing here. A device linked to no machine keeps the
unpaired default (the owner's desktop and browser everything, a phone `view`).

**`/secure-mcp` authenticates peer daemons.** The peer must be a registered `host`
key; `machine` and device id are derived from the registry, and a handshake frame
that claims otherwise is refused. `allowed_devices: None` admits the target
machine's daemon only; a list compares the verified id alone.

### Round-2 council amendments

**A live secret opens PSK pairing, and only its owner closes it.** Storing a
one-time secret in `SecureService` now also flips `PairingPolicy::allow_psk_pairing`;
consuming or clearing the secret flips it back. The direct-pairing watcher therefore
works from `SecureOptions::new` with no `with_psk`, and a watcher-armed secret can
pair a device. The watcher remembers the secret it installed and clears only that
value: an operator's `H4RN_PAIRING_PSK` is never replaced, and its expiry never
clears the operator's secret. A live file that would replace another secret is
logged and left alone.

**A consumed or expired direct pairing is deleted from disk.** The transport's
consumed hook runs before the device is authorised and removes the matching
`direct-pairing.json`; the watcher deletes expired files and drops the armed scopes
with the secret. A restart before the old expiry can no longer re-arm a QR that
already paired one device. If the delete fails, the hook records the BLAKE3 hash of
the consumed PSK in `direct-pairing.consumed` and the watcher refuses to arm a file
whose hash is listed; the marker stores no secret and is best effort, so a write
that also fails leaves only the in-memory consumption until the file expires.

**A direct pairing without `--scope` grants `view` and `approve`.** A QR can be
photographed and the LAN/tailnet window is short, so `terminal`, `files` and
`admin` need an explicit `--scope`. The same safe default applies to a file with
no `scopes` field and to an operator PSK with nothing armed.

**Every relay-provisioned device waits for the host.** `DevicePaired` and snapshots
now insert the key as *pending*: registered, with its requested scopes stored but
not effective, and deliberately absent from the transport allowlist. A snapshot
refreshes the requested scopes but never promotes a pending entry. Settings →
Devices shows the SAS and a Confirm/Reject action, served by the
`ConfirmPairing { device_id, confirm }` request (`admin`). Confirming admits the
key on the transport; rejecting removes and revokes it. This closes the window in
which a malicious relay could substitute a key and use the granted scopes before
anyone compared the codes.

The gate applies to QR pairings too. A QR pins the daemon key for the phone, but
the host still learns the *device* key from the relay, so the host must confirm it
just like a typed code. Pending entries do not expire: an undecided device stays
blocked and listed until the host confirms or rejects it, including across a
restart (the relay snapshot rebuilds the confirmation card).

**Registry and peer lifecycle are reconciled, not overwritten.** A client insert
never replaces a `host` entry: the peer daemon's MCP authorisation survives a
device re-pair. After a restart the in-memory peer directory is empty, so the first
authoritative peer report now reconciles the *persisted* connect-provenance host
entries too: a host key absent from the peer set is removed from the registry,
revoked from the transport and its sessions closed. Terminal ownership and the
remote audit trail use the registry id (or the verified key when a direct
pairing has no connect id), never the device id a remote client claimed in
`Hello`.

### Round-3 council amendments

**The phone compares the SAS on the QR path too, and waits for the host.**
Claiming a QR used to activate the phone immediately, but since round 2 the host
keeps every relay-provisioned device pending until it confirms the SAS, so the
phone connected to a host that had not admitted it. The phone now derives the
string in Rust from its own key and the daemon key *pinned by the QR* (not the
copy connect echoes back), shows it, and pins nothing until the person taps
"They match". After that the phone shows a waiting state until the transport
comes online, which only happens after the host confirms. A timeout keeps the
comparison screen with an explanation and a retry; it is never reported as
paired. The typed-code path uses the same screen and ordering. This is a
deliberate two-sided gate: the phone pins the daemon key it will trust, and the
host admits the device key it learned from the relay.

**Connect entries start a run unverified; direct pairings do not.**
`devices.json` still records connect clients and peer hosts, but `open()` loads
those entries with `verified = false`: they are neither in the transport
allowlist nor authorised, and `scopes_for_key`/`authorization` return nothing,
until the first authoritative source for this run reconciles them — a connect
snapshot for clients, a peer report for hosts. `admitted_keys()` is what startup
passes to the transport, so a device revoked while the daemon was offline from
connect cannot be re-admitted by a restart. Direct-provenance pairings load
admitted because they do not depend on connect. The trade-off is explicit:
connect-paired phones cannot use a direct or tailnet path until the daemon has
reached connect once in this run. An entry still keeps its `device_id`, and
`registered_role()` ignores verification where the registry only needs to know
what a key is (for example, refusing to re-role a peer). Pending state is still
serialised: a relay-announced device stays pending and unadmitted across a
restart until the host decides.

**A failing consumed hook refuses the pairing, and keeps the PSK closed.**
`consume_psk` now takes a fallible hook. If invalidating the one-time
`direct-pairing.json` fails, the transport returns `NotPaired` rather than
authorising the device. The secret is already consumed, and the failed delete
leaves a consumed marker so the watcher does not re-arm the file on a restart
(best effort: if the marker write also fails, only the in-memory consumption
protects the QR until it expires). The daemon logs the hook error; the transport
cannot do more than refuse.

**A registry write failure is reported, not swallowed.** `persist` returns a
`PersistError`; `mutate` returns both the change's result and the write result.
Admissions (confirming a pending device, inserting or updating a pairing) roll
back in memory when the file cannot record them, and the error reaches
`ConfirmPairing` and the UI, so a device is never admitted for this run if it
would not be admitted after a restart. Revocations deliberately do not roll
back: a failed write keeps the key revoked in memory and appends it to
`devices.revoked`, a sidecar that `DeviceRegistry::open` applies before allowing
anyone and then clears after a successful rewrite. The sidecar is the retry that
survives a crash, and the UI still sees the error. Peer-host updates log the error
and skip admitting the peer rather than pretending the write succeeded.

### Round-6 follow-up amendments

**The first record is validated before anyone is paired, and the pre-attach phase has a deadline.**
The `Open` record is decoded before the authorisation step, and a PSK-authorised device that
presents a resume token is refused with `NotPaired` before pairing (a legitimate client never sends
both). Any failure to open the first record gets the same `NotPaired` reject for every key, so it
cannot distinguish allowed from unknown keys. A correct secret presented by an already-allowlisted
device leaves the secret armed, matching the round-5 rule that paired devices do not consume it.
`SecureService::accept` is bounded by `handshake_timeout` (10 s) and the post-reject restart wait by
`restart_timeout` (5 s), enforced inside the transport so no caller can forget the deadline.

**The client waits longer for the first reply than for a probe.** Between the handshake and
`Welcome` the daemon records a new pairing durably (registry write, pairing-file delete). The
client's 1 s `path_timeout_ms` applied as soon as the channel existed, so on a slow or loaded disk
it declared the path dead, dropped the late `Welcome` and ended with "transport client stopped"
once the daemon closed the idle socket. A path now uses `establish_timeout_ms` (10 s) until its
first authenticated record arrives, and `path_timeout_ms` after that.

## ADR-043: App updates live in the shell; harness updates live in the daemon

**Status:** Accepted

Two things called "update" have different owners. The **desktop app** is replaced by the Tauri
updater, so the shell owns the check, the six-hour timer, the download and the relaunch, and the
view only renders `h4rn://update-checked` and `h4rn://update-progress`. A check that cannot run
(no endpoint, the `__H4RN_UPDATER_PUBKEY__` development placeholder, offline) is logged and never
shown: an update notice is a convenience, not an error. "Later" is a view-side snooze that the next
check clears. The saved auto-check choice is the view's (`localStorage`), pushed to the shell at
startup, and the shell waits 20 seconds before its first check so that choice arrives first.

The **harness CLIs** are installation facts of a host, so the daemon owns them. It reads each CLI's
version through the existing detection, asks the npm registry for the latest version of
`@anthropic-ai/claude-code`, `@openai/codex` and `opencode-ai` (cached three hours; an offline
registry is cached for five minutes and reported as unknown, never as an error), and classifies the
install: the CLI's own updater first (`claude update`, `opencode upgrade`), then `npm i -g` for a
`node_modules` install or `bun add -g` under the bun global directory, otherwise a command shown to
the person and never run (Homebrew, a distro package, a manual copy). Antigravity has no registry
source, so its latest version is unknown and no update is offered.

`UpdateHarness` replaces a binary a live session may be running, so it needs the admin scope and is
refused while any thread on that harness has an active turn. The command runs as a child process
with no shell and its arguments as an array, streams output as transient `HarnessEvent` frames
(not replayed after a reconnect; the client re-reads the versions), then re-detects the version so
the result names what is on disk, not what the registry promised. The registry client and the
process runner are injectable seams, so no test touches the network or a real global CLI.


## ADR-044: A guest link is a narrow HTTP surface bound to one thread and one browser

**Status:** Accepted

A guest link exists so one teammate can follow one thread without an account.
That rules out the device protocol: a guest has no Noise identity, no pairing
and no access token, and inventing a device for them would widen every scope
check. The link is therefore a bearer URL and the daemon answers a small HTTP
surface instead of upgrading `/ws`.

The token is 256 random bits. The journal stores its BLAKE3 hash and the hash of
the browser's cookie, never the raw values; both comparisons are constant time.
The raw token lives only in the running daemon's memory, so a restart keeps a
guest working but the owner must create a new link to copy it again. That is a
deliberate cost: a stolen journal cannot be replayed as a link.

A link names exactly one thread. The client never sends a thread id, so a
malicious page cannot ask for another thread; every read, submission and blob
fetch resolves the token first and then uses the link's thread. The surface has
four routes: the page, a snapshot of events after a sequence, a message
submission, and one attachment from a message in that thread. Events pass through
an explicit allow-list projection: the workspace path (`ThreadUpserted`),
approvals, filesystem events, subagent threads and MCP administration are absent;
turn changes are stripped and attachment `local_path` values are cleared. Tool
calls lose their raw arguments, and a file-editing tool loses its output too, so
a Codex file change's structured diff or an `apply_patch` body never appears.

Loading the page does not claim the link. The page offers a short-lived unclaimed
cookie and the first state read or submission that presents it binds the browser
atomically. A link-preview crawler that only fetches the URL therefore cannot
take the link, and a cookie-less second fetch changes nothing. A submission must
be a same-origin JSON POST, and its token and binding are checked from the
headers before the body is read.

A guest message is not a turn. It is a row in the journal and an event,
`GuestRequested`, which raises a hand in the lifecycle and renders as a Request
at the end of the thread; `SendGuestRequest` uploads its files, calls the normal
`SendMessage` path with the thread's current permission mode, and
`DismissGuestRequest` deletes the files. A submission reserves the pending
budget (8 messages, 20 MB of text and files) before it writes any file, then
inserts the request in one transaction whose guard requires the link to still
exist and the Labs switch to still be on; a racing Stop sharing, new link,
settle or switch-off therefore leaves no request and no files. The row becomes
visible to the owner, and its `GuestRequested` event is raised, only after the
files are written; both steps happen while the submission lock is held, so
ending a link can never race a card into existence. Send and Dismiss claim a
request with one conditional update, so two actions can never run the same
message twice.

Every removal of a request raises `GuestRequestResolved` before its row is
deleted, and the resolved event names its request. A crash between the claim and
the event therefore leaves a row the startup sweep can resolve, and a repeated
event from that sweep cannot clear another guest's hand. The periodic sweep
leaves a `sending` or `reserving` row alone while a task may still be reading
it; only the startup pass, where no reader can exist, recovers it.

Ending access and deleting files are separate steps. Ending a link deletes its
row first and removes its page-load cookies, then settles waiting messages; a
disk error never leaves a token live. A periodic sweep (also run at startup)
removes expired links, ends any link whose thread has settled, discards their
files, and retries cleanup for requests whose link or turn is already gone.
Settling a thread (a person, the 24-hour idle rule, a merged branch), stopping
sharing, creating a new link, the 24-hour expiry and turning the Labs switch off
all end a link; a settled thread refuses a new link, a submission and a Send or
Dismiss, and turning the switch back on does not revive one.

A guest link has no pairing scope. It carries its own token and no device
identity, so `PairScope` has no guest variant and pairing can never grant one.
The narrow surface is enforced by the token's single thread, not by a scope.

When the machine is linked to Connect, the link names
`<connect>/guest/<machine>/<token>`. Connect serves the guest page itself, from a
fixed document admitted by a hash-based CSP; it never relays daemon HTML onto its
own origin. Each exchange travels to the daemon over its existing authenticated
relay socket and is answered by that daemon only: a waiter is bound to the
selected daemon's device id, and a reply from any other device is ignored.
Bodies are split into bounded frames, so a 10 MB upload never grows a shared
WebSocket frame; Connect refuses an exchange over the guest limit before it
reaches the socket, and rebuilds every response header, including the binding
cookie's path, which must name the public `/guest/<machine>/<token>` prefix.
Every relayed answer carries `Content-Security-Policy: sandbox; default-src
'none'`, and a PDF or opaque file is served as an attachment rather than opened
in Connect's tab. Guest routes are traced by template, never by raw URI. The
payload is plaintext at that hop, as the rest of the relay path is TLS to
Connect plus Noise only for device sessions; a guest has no Noise key.

Without Connect the daemon names its own loopback listener. A direct link is a
bearer token and the daemon has no TLS listener, so it is not offered over a LAN
address; the share dialog says the link works only on this machine and points to
Connect for a teammate elsewhere. Only the owner or an admin-scoped device may
copy the URL; a view device gets the link metadata with `url: null`.

The guest page polls its snapshot every couple of seconds rather than opening a
second long-lived socket. That keeps one transport (HTTP) working through both
the direct address and the relay proxy, and the thread still follows live work
within that interval.

## ADR-045: A queued message is durable; a steer needs an attributable turn

**Status:** Accepted

`SendMessage` still appends one message, but while a turn runs it now has two honest outcomes.
**Queue** (the default) stores the message in the thread row's `queued_json` with a stable
`QueuedMessageId`, so the queue survives a daemon restart in its order, and emits a summary instead
of a transcript row: queued messages are not yet part of the conversation. **Steer** delivers the
text into the turn that is already running, adds the user row to that turn, and never also queues
it. With no turn running, a steer is an ordinary send.

**Only Codex steers.** Codex app-server has `turn/steer` with an `expectedTurnId`, so the server
itself refuses a request aimed at a turn that has ended. Claude Code is not offered it: its
stream-json input is a queue of user frames over one long-lived conversation, and a frame written
while a turn runs is either read between tool calls and folded into that turn's single `result`, or
read after the turn's `result` was emitted and answered as a second turn with its own `result`.
Measured against 2.1.330 both happen, and nothing in the stream says which: a mid-turn steer that
carried a Bash call produced one `result` with `num_turns: 2`, while two frames written before the
process read them produced two `result`s. Settling on the first `result` would put the steer's
answer on the next turn, and holding the turn open for a second `result` would hang whenever the
first one already contained it. h4rn's durable queue already gives Claude the honest follow-up, so
Claude advertises no steer; the daemon refuses it with a typed `Unsupported` error rather than
guessing. OpenCode's HTTP prompt starts a queued message and ACP has one prompt at a time, so they
do not advertise it either. Claude's steering was withdrawn in the council's first review round.

A steer is delivered **at most once**. It names the turn the client observed (`SendMessage.turn_id`)
and the daemon refuses a stale id and a turn whose first prompt the harness has not accepted yet.
Sending now from the queue claims the message durably before the adapter sees it: the queue row is
journaled without the message first. If the journal write fails the claim is undone and nothing was
delivered; if the adapter definitely refuses (unsupported, missing binary, a protocol error answer)
the message goes back where it was; if the outcome is unclear (a timeout, a dead transport) the
claim stands and the error is reported, because a second automatic delivery is worse than a row the
person has to retype. The claim also reads the message under the same lock that removes it, so an
edit committed in between cannot send text the person already replaced.

Queue edits, removals, moves and Send now are one daemon request (`QueueMessage`). Every mutation
and the promotion of the next turn take the same thread-record lock, so a message that has just
started is refused with `Conflict` rather than edited or removed after the harness already got it.
A mutation is published only after the journal accepted it; a failed write restores the in-memory
queue exactly, so memory and storage never disagree. `Send now` steers when the running harness can,
otherwise moves the message to the front (and starts a turn if none runs).

**Starting work by hand cancels an armed auto-resume.** An ordinary send, an idle promotion of an
older queue, `Send now` and a steer into a paused turn all take the thread's `scheduled_limit`, clear
the summary's resume target and limit, cancel the ledger schedule, and publish
`LimitResumeReleased` when the pause really held the pending prompt. Without that, the schedule
fired a stale resume later and its guard kept the next queued message from ever being promoted.

The queue's **contents are not in `ThreadSummary`**. A full queue is unbounded while a paired
transport refuses a frame over 512 KiB, so carrying it in every summary made a large queue break the
connection. The summary carries `queued_count` and a `queue_revision`; the rows come from
`GetThreadQueue` in bounded pages (whole messages only, at most 100 and about 256 KiB per page) and a
client pages with `offset`. A `QueueUpdated` reply names the revision it came from, so a reply that
arrives after a newer summary is ignored instead of putting back a message that already started.

The composer keeps three texts apart while editing a queued message: the edit buffer in the box, the
message's saved text, and the thread's own draft (which stays in storage). A second Edit keeps the
draft the first one displaced, another tab's draft write never replaces an active edit, and when the
message starts under the edit the composer refills only with text that actually changed.

Clients choose a per-device default for follow-ups (Queue or Steer) in Settings → Chat. Enter (or
Cmd/Ctrl+Enter when `Enter inserts a new line` is on) uses that default; Cmd/Ctrl+Enter (or adding
Shift in multiline mode) uses the opposite action. `Cmd/Ctrl+Shift+Enter` steers the oldest queued
message while a turn is really running, and `Alt/Option+Up` at the start of the composer edits the
newest one; both are rebindable.
